# API: engine/physics

[← README](../README.ru.md) · [core](api-core.md) · [world](api-world.md) · [scene и render](api-render.md) · [gpu](api-gpu.md) · [assets и entity](api-assets.md) · [sprite](api-sprite.md) · [prop](api-prop.md) · [rig](api-rig.md) · [anim](api-anim.md) · [physics](api-physics.md) · [script](api-script.md) · [video](api-video.md)

Слой, в котором мир перестаёт быть картинкой и начинает идти. Две несвязанные
половины под одной крышей:

- **твёрдые тела** — воксельные модели, которые падают, сталкиваются,
  укладываются в стопку и скрепляются связями;
- **контроллер персонажа** — прямоходящая коробка, которая ходит и не проходит
  сквозь стены, и которая намеренно **не** твёрдое тело.

Общего у них ровно одно: и то и другое встречается с `World`, а не друг с
другом. Пользуются этим `scene_spike`, `scene_sandbox`, `scene_live` и игра.

Про картинку слой не знает ничего: в `engine/physics/` нет ни одного включения
из `render/`.

---

## Почему здесь нет нового объектного типа

`Prop` уже нёс позицию, три угла и равномерный размер вокселя, и в собственном
комментарии говорил, что набор уплощает каждое размещение в жёсткое
преобразование с равномерным масштабом. Это ровно то состояние, которое
интегрирует физика, — понадобилось только место под скорость и массу.

Единственная подстановка — **ориентация**. Углы Эйлера точны везде в этом
движке, потому что каждый сустав здесь одноосный, и [слой
анимации](api-anim.md) говорит об этом прямо. Тело под моментом крутится вокруг
оси, которая сама движется, — это тот самый случай, который довод исключает.
`Quat` появился для него.

## collider.hpp

```cpp
struct ColliderBox { Vec3 center, halfExtents; };   // локально, от центра масс

struct Collider {
    std::vector<ColliderBox> boxes;
    Vec3  centreOfMassVoxel;      // центр масс в воксельных координатах модели
    Vec3  boundsMin, boundsMax;
    float radius;                 // сфера вокруг них — то, что спрашивает широкая фаза
    float volume;
    bool  empty() const;
};

Collider buildCollider(const VoxelModel& model, float voxelSize);
Mat3     inertiaTensor(const Collider&, float density, float* massOut);
```

Форму спрашивают тысячи раз в секунду, и плотная сетка — неверный ответ:
проверять кувыркающуюся модель ячейка за ячейкой против мира значит платить
квадратично тем самым, ради чего воксели и брались.

Выпуклая декомпозиция — честно трудная задача геометрии. Воксели выдают задачу
полегче: множество сплошных ячеек **уже** есть объединение осевых единичных
кубов, поэтому жадное слияние в коробки покрупнее **точно**, а не приближённо.
Предмет в шестнадцать вокселей обычно падает до нескольких десятков коробок,
плита или доска — до одной.

> **Два инварианта, и оба проверяются.** Коробки **покрывают каждый сплошной
> воксель** и **нигде не пересекаются**. Вместе это значит, что разбиение —
> разбиение, а значит сумма объёма и инерции по коробкам равна сумме по
> вокселям. Это единственная причина, по которой `inertiaTensor` вправе не
> смотреть на сетку вовсе, и `test_physics` требует обе половины: покрытие и
> отсутствие пересечений отдельно.

`voxelSize` — мировых единиц на воксель, `1/16` для предмета игрового размера,
как у `Prop`.

Плотность **однородна**, и это видимое допущение: пустотелый фонарь
кувыркается как сплошной кусок того же силуэта. Взвешивание по вокселям
заставило бы разбиение перестать сливать коробки, то есть отменило бы то, ради
чего оно есть.

## body.hpp

```cpp
struct RigidBody {
    Vec3 position;              // мировая позиция ЦЕНТРА МАСС
    Quat orientation;
    Vec3 linearVelocity, angularVelocity;

    float invMass;              // 0 — бесконечная масса, тело неподвижно
    Mat3  invInertiaLocal;

    float restitution = 0.0f;   // 0 — садится намертво
    float friction = 0.6f;

    const Collider* collider;   // обязан пережить тело
    float voxelSize = 1.0f / 16.0f;

    bool  sleeping;  float restSeconds;

    bool isStatic() const;
    Mat3 invInertiaWorld() const;
    Vec3 velocityAt(Vec3 worldPoint) const;
    void applyImpulse(Vec3 impulse, Vec3 worldPoint);
    void applyAngularImpulse(Vec3 impulse);   // пара: крутит, не двигая
    void wake();
};

void setMassFromCollider(RigidBody&, const Collider&, float density);
Mat4 bodyToWorld(const RigidBody&);
```

`position` — центр масс, **не угол модели**: свободное тело вращается вокруг
центра масс, и любое другое начало пришлось бы каждый шаг поправлять на
смещение.

Хранится обратная масса, а не масса. Ничего в солвере не ветвится на
«статическое»: бесконечная масса выпадает из той же арифметики, что и тяжёлая.
Нулевая плотность или пустой коллайдер оставляют тело статическим.

### bodyToWorld — единственное место, знающее про смещение

Физика работает в системе, центрированной на центре масс, а рендерер — от угла
модели. Кто-то обязан держать смещение между ними, и это `bodyToWorld`,
возвращающий преобразование из **воксельных** координат модели в мир — ровно
то, что принимает `PropSet::addTransformed`.

Одно место по той же причине, по которой существует `entityJointToWorld` (см.
[архитектуру](architecture.md#вещь-в-руке--это-проп-а-не-часть-персонажа)): две
копии формулы размещения согласны до того дня, когда одна из них меняется, и
тогда тело и его изображение расходятся так, что это читается как кривая
модель, а не как баг.

```cpp
props.clear();
for (const Spawned& piece : spawned)
    props.addTransformed(piece.model, bodyToWorld(physics.body(piece.body)), piece.tint);
props.build();
scene.props = &props;
```

Это весь шов между физикой и кадром. `test_physics` требует его точности
численно.

## contact.hpp

```cpp
struct Contact {
    Vec3  position;         // мировое пространство
    Vec3  normal;           // единичная, от B к A
    float depth;
    int   bodyA, bodyB;     // bodyB < 0 — статический мир
    uint64_t feature;       // имя пары признаков, для warm starting
    float normalImpulse, tangentImpulse[2], pseudoImpulse;
};

void bodyBounds(const RigidBody&, Vec3& lo, Vec3& hi);
void collideBodyWithWorld(const RigidBody&, const World&, std::vector<Contact>& out);
void collideBodies(const RigidBody& a, const RigidBody& b, std::vector<Contact>& out);
```

Останавливает ли ячейка тело и жидкость ли она — спрашивают у мира:
`World::collides` и `World::isFluid` читают `BlockDef::solid` и `BlockDef::fluid`
из палитры, с которой мир построен. Воздух и вода оба проходимы, и ровно одна
из них держит, поэтому это два флага, а не один.

Раньше здесь стояли `blockIsFluid(BlockId)` и `blockCollides(BlockId)`,
сравнивавшие идентификатор с водой и лавой встроенной палитры. Это работало
ровно для неё: физика обязана была знать блок по имени, а блок, который
зарегистрировали снаружи, выходил твёрдым молча.

`bodyB < 0` означает мир, и отдельной записи ему не нужно: неподвижная вещь и
вещь с бесконечной массой ведут себя в солвере одинаково.

**Мир как соперник — проще, а не сложнее.** Тело в обычном движке встречает суп
треугольников: нужна ускоряющая структура для меша, а тонкий или неверно
ориентированный треугольник — вечный источник тел, проваливающихся сквозь пол.
Здесь широкая фаза — целочисленная арифметика по карте чанков, той же самой,
которую обходит трассировщик, и все кандидаты одинаковой формы. Обе половины
сводятся к одному тесту узкой фазы: ориентированная коробка против
ориентированной, где ячейки мира тривиально ориентированы.

### Вето на швы решётки

SAT сообщает ось наименьшего проникновения. На решётке этот ответ бывает
буквально верным и практически негодным: грань ячейки, за которой стоит ещё
один сплошной блок, — не поверхность, а **шов между двумя блоками пола**.

Без вето коробка, скользящая по ровной земле, цепляется за каждый шов: солвер
периодически велит ей выйти вбок через грань, за которой стоит следующий блок.
Симптом читается как «пол липкий», а не как ошибка в контактах.

Поэтому направление, выбранное как ось выталкивания, проверяется на соседа, и
при сплошном соседе отвергается **как выбор** — но не как тест разделения:
разделяющей осью оно остаться вправе.

> **Вето смотрит на направление, а не на список.** Коробка, стоящая по осям
> мира, имеет свои оси равными мировым, и вето, доверяющее тому, из чьего
> списка ось пришла, обошлось бы дубликатом — то есть отсутствовало бы ровно
> там, где нужнее всего, потому что «по осям мира» и есть обычный случай.

### feature — имя, без которого нет warm starting

Контакты пересоздаются из ничего каждый шаг. Без имени невозможно сказать «это
тот же угол на том же блоке, что и в прошлый раз», а это предложение и есть
весь warm starting. Имя — хеш, а не упакованное поле, потому что координаты
ячеек не ограничены; коллизия стоит одного плохо засеянного контакта, а не
корректности.

### Манифолд — отсечение граней, и это вторая попытка

Первая брала каждый угол одной коробки внутри другой. Просто, верно для
торчащего угла и негодно для единственной расстановки, которую песочница
делает всё время: плоскость на плоскости.

Там углы лежат **на** границе соседа, а не внутри неё, поэтому засчитывается
угол или нет — решается в последних битах float, и ответ меняется каждый шаг.
Пара, у которой должно быть четыре неподвижные точки, получала ноль-две
подвижных; этого мало, чтобы коробка не вращалась. Она наклонялась, а
наклонившись — правда выводила углы наружу, и через несколько секунд оказывалась
внутри того, на чём лежала. **Ящик нельзя было поставить на ящик.** Пять кубов
стояли ровно потому, что успевали заснуть до начала распада, и это делало
поломку невидимой.

Теперь ось-победитель SAT называет **опорную** грань, самая противоположная ей
грань второй коробки становится **отсекаемой**, её четырёхугольник режется по
четырём боковым плоскостям опорной, и остаётся то, что за опорной плоскостью.
Лицом к лицу это четыре точки, каждый шаг те же и с теми же именами, что бы ни
делало проникновение в последних битах.

Заодно отпала асимметрия, ради которой существовал отдельный флаг: глубина
меряется до настоящей плоскости для каждой точки, а не берётся одна на пару. У
наклонной коробки углы правда на разной глубине, и одно SAT-число
перекорректировало мелкие.

Осталось два места, где старый способ по-прежнему прав и применяется:

- **Ребро о ребро.** Грани, до которой отсекать, там нет, и не нужно: угол
  действительно один и в одном месте. Одна SAT-глубина там — честное число.
- **Смещение в пользу грани.** Две коробки, лежащие лицом к лицу, разделены
  гранью и несколькими рёберными осями почти одинаково, и без смещения
  победитель прыгал бы на шуме float — а вместе с ним прыгала бы вся форма
  манифолда. Ребро должно выиграть у грани с запасом, иначе выигрывает грань.

## constraint.hpp

```cpp
enum class ConstraintKind { Distance, BallSocket, Weld, Hinge };

struct Constraint {
    ConstraintKind kind;
    int  bodyA, bodyB;        // bodyB < 0 — якорь в мире, anchorB мировая точка
    Vec3 anchorA, anchorB;    // в системе своего тела, от центра масс

    float distance;  bool rope;      // Distance: длина; rope — только не пускать врозь
    Vec3  axisA, axisB;              // Hinge: ось в системе каждого тела
    Quat  rest;                      // Weld/Hinge: поза в момент создания

    float breakImpulse;  bool broken;   // 0 — не ломается
    float friction;                     // в том, что связь оставляет СВОБОДНЫМ
    bool  motor;  float motorSpeed, motorTorque;
};

Constraint weldAt(a, ia, b, ib, Vec3 worldPoint);
Constraint ballSocketAt(a, ia, b, ib, Vec3 worldPoint);
Constraint hingeAt(a, ia, b, ib, Vec3 worldPoint, Vec3 worldAxis);
Constraint ropeBetween(a, ia, b, ib, Vec3 worldA, Vec3 worldB, float length);
Constraint rodBetween(a, ia, b, ib, Vec3 worldA, Vec3 worldB, float length);
```

Тела, которые падают и укладываются в стопку, — демонстрация. Тела, которые
можно **скрепить**, — игрушка, и каждый инструмент жанра (сварщик, верёвка,
гидравлика, двигатель на петле) это одна из четырёх связей плюс способ указать
на две вещи.

Решаются они в том же цикле последовательных импульсов и в те же два прохода,
что контакты, — отдельной системы здесь нет. Отличий ровно два: строки связи
умеют тянуть, а не только толкать, и связь **переживает шаг**, а значит
объединяет свои два тела в один остров сна.

| Вид | Строки |
|---|---|
| `Distance` | одна вдоль линии между якорями; `rope` делает её односторонней |
| `BallSocket` | три, держат точки вместе, вращение свободно всё |
| `Weld` | шаровая плюс три угловых, держат взаимную ориентацию `rest` |
| `Hinge` | шаровая плюс две угловых, свободно вращение вокруг оси |

Разницы между верёвкой и стержнем нет никакой, кроме `rope`: верёвка не пускает
расходиться и ничего не делает при сближении. Отдельного вида для **гидравлики**
тоже нет — это `rodBetween`, чью `distance` кто-то меняет на ходу.

Помощники `...At` записывают текущую взаимную позу, поэтому связь, сделанная на
месте, держит тела там, где они уже стоят, а не подтягивает их к какой-то
канонической расстановке.

### Трение, мотор и разрыв — не украшения

- **Трение.** Петля без трения — маятник, который никогда не остановится:
  физика верная, для песочницы негодная, потому что вещи там обязаны прийти в
  покой, чтобы остров уснул и перестал стоить. Контакт берёт предел трения из
  нормальной силы, которую уже несёт; у связи такой силы нет, поэтому предел
  **задают**, а не выводят. Свободное зависит от вида: ось у `Hinge`, все три
  вращения у `BallSocket`, линия у `Distance`. У `Weld` свободного нет, и трение
  на нём не делает ничего.
- **Мотор.** `motorSpeed` — относительная угловая скорость вокруг оси, рад/с.
  `motorTorque` ограничивает импульс за шаг и не опционален по смыслу: мотор без
  предела выходит на любую скорость за один шаг и превращает связь в рычаг,
  двигающий мир. Работающий мотор **заменяет** трение, а не добавляется к нему,
  поэтому мотор на нулевой скорости — тормоз.
- **Разрыв.** `breakImpulse` — импульс за шаг, выше которого связь сдаётся.
  Интереснее половина постройки контраптиона — смотреть, как он ломается.

> Связи добавляются после тел, которые называют. Связь на удалённом теле
> снимается вместе с ним, а `removeConstraint` снимает её руками; **сломанная**
> — это другое и остаётся в списке, потому что она произошла, а не была
> отменена.

### Пределы поворота: конус и кручение

```cpp
float coneLimitDegrees  = 0.0f;   // насколько отклоняется от rest
float twistLimitDegrees = 0.0f;   // насколько проворачивается вокруг себя
```

Только у `BallSocket`, и регдолл — то, ради чего они есть. Шесть конечностей на
неограниченных шарнирах — мешок деталей: колено складывается не туда, голова
проворачивается кругом, локоть проходит сквозь грудь. Солвер при этом не
ошибается — шаровой шарнир правда оставляет свободными все три вращения, — и
трение не помогает, потому что трение сопротивляется движению, а не запрещает
позу.

Двух углов, а не одного, потому что сустав не гнётся и не крутится одинаково: у
плеча размах почти в полкруга и кручения почти нет. Пара — это swing-twist
разложение отклонения от `rest` вокруг `axisB`, то есть вокруг **собственной оси
конечности в системе родителя**. Умолчание `+Y` подходит всему, что висит на
теле, а конус симметричен, так что направление знака решает только, какое
кручение считать положительным.

Ряды односторонние: внутри предела ограничения нет вообще, за пределом ряд может
толкать назад и не может тянуть. Тест гоняет обе стороны — с пределом и без, —
потому что тест сустава ровно этого вида умеет пройти вхолостую: конечность,
которая никогда не доходит до предела, согласится с любым.

Замерено: конечность, получившая боковой пинок, отклоняется на 69.6° свободно и
на 25.7° с конусом в 25°; раскрученная вокруг себя — на 180° свободно и на 20.0°
с пределом в 20°.

## pick.hpp

```cpp
struct BodyPick {
    int   body = -1;
    float distance = 0.0f;
    Vec3  position, normal;   // где встретил и куда смотрит поверхность
};

bool pickBody(const PhysicsWorld&, const Ray&, float maxDistance, BodyPick&);
```

Луч по телам. Рендерер отвечает на похожий вопрос — `intersectScene` находит
проп под лучом — и намеренно на другой: он работает по **нарисованному** набору,
уплощённому и замороженному при сборке кадра, и отдаёт материал. Инструменту
нужно то, что будет здесь и на следующем шаге, и нужно знать, **какое именно**,
чтобы наложить связь.

Линейный проход со сферическим отсевом — та же форма, что у широкой фазы рядом,
и честна по той же причине. Спящие тела находятся: сон — оптимизация, а
инструмент, не умеющий поднять то, что уже улеглось, не умел бы поднять почти
ничего.

`position` — не украшение. Без него физган держит любой ящик за середину, и
доска, взятая за край, разворачивается в руке в момент захвата.

Против мира по-прежнему `raycast` из `world/raycast.hpp`, и инструменту нужны
**оба**: взять ящик сквозь стену — это не дальнобойность, это отсутствие стены.
Сравнить две дистанции и взять ближнюю.

### Удаление: индекс — это указатель

`remove` снимает тело с симуляции, снимает вместе с ним каждый сустав, который
его называл, и **возвращает слот в оборот**. Поэтому индекс живёт по правилам
указателя: он верен, пока названное им тело существует, и молча называет
кого-то другого после. `alive` отвечает на первую половину; на вторую ответить
нечем, так что тот, кто держит индексы — регдолл, хватка физгана, список
заспавненного скриптом, — обязан забыть их в тот момент, когда удаляет.

Слоты не выдавать заново было вторым вариантом и не масштабируется: широкая
фаза квадратична по числу слотов, и песочница, оставленная работать, стала бы
тратить кадр на перешагивание мёртвых. Отсюда же и то, что удаление **опустошает**
слот, а не помечает его: у пустого `RigidBody` бесконечная масса, а все линейные
проходы шага такие уже пропускают — новому условию негде забыться.

Две вещи, которые удаление обязано сделать помимо этого, и обе выяснились на
тестах:

- **Разбудить то, что на нём держалось.** Ящик, висящий на сварке, засыпает; ни
  одна строчка шага не спрашивает, существует ли ещё то, на чём он висит.
  Убрать якорь — и он остаётся спать в воздухе навсегда. То же правило, что и у
  гидравлики, менявшей длину и не двигавшей ничего: оптимизация, проглатывающая
  указание, — это баг, а удаление и есть указание.
- **Посолить ключ импульсов.** Warm starting **применяет** сохранённый импульс
  до первой итерации. Без соли новое тело в освободившемся слоте получает
  историю покойника — и стартует пинком, который держал кого-то другого.

### Заморозка — третье состояние, а не одно из двух

`setFrozen` держит тело на месте, пока его не отпустят.

*Спящее* — это солвер решил, что тело остановилось, и всё, что его касается,
будит его; здесь именно этого быть не должно. *Статическое* — то, что и не
собиралось двигаться. Замороженное — динамическое тело, которому велели
перестать им быть, и функцией это делает то, что оно обязано остаться
**твёрдым**: в песочнице заморозка — это способ построить стену по доске.

Сделано собственной массой, а не веткой: масса уходит в бесконечность, настоящая
ждёт в теле, и каждая строчка солвера обращается с ним ровно как с чем угодно
неподвижным. Отсюда одна правка, которая была не видна, пока ничто не бывало
статическим: широкая фаза раньше пропускала **любую** пару с неподвижным телом,
и на примороженную доску ничего нельзя было положить. Теперь пара пропускается,
только если неподвижны или спят обе.

Размораживает `setFrozen`, а не `RigidBody::unfreeze`, по одной причине: острова
намеренно не объединяются через неподвижное тело, поэтому ящик, спящий на
доске, узнать о том, что доска снова падает, может только если ему сказать.

### Шаг обязан быть фиксированным

`step` делает шаг ровно на `dt`. Аккумулятор держит вызывающий и зовёт её целое
число раз:

```cpp
const float kStep = 1.0f / 120.0f;
accumulator += dt;
int steps = 0;
while (accumulator >= kStep && steps < 8) {   // потолок: иначе просадка кадра
    physics.step(world, kStep);               // догоняется вечно
    accumulator -= kStep;
    ++steps;
}
```

Солвер, которому дают переменный `dt`, меняет жёсткость вместе с частотой
кадров: та же коробка укладывается по-разному на быстрой машине — и заодно
перестаёт быть воспроизводимой.

### Что нужно телу, чтобы встать

«Падает» — легко, «приходит в покой» — вся сложность. Убери одно из четырёх, и
что-нибудь перестанет успокаиваться:

| Что | Без чего |
|---|---|
| трение | вечно скользит по ровному полу |
| `penetrationSlop` | коррекция и гравитация перебрасывают миллиметр, коробка гудит |
| `warmStart` | стопка каждый шаг заново открывает свои силы и проседает |
| сон **по островам** | коробка на движущейся коробке засыпает под ней |

Поэтому `test_physics` утверждает про **неподвижность** и про высоту стопки, а
не про положение. `warmStart` оставлен переключаемым нарочно: это утверждение,
которое положено измерять, и тест строит стопку обоими способами.

### Псевдоскорость

Выталкивание — поправка к **положению**, и делать её добавлением настоящей
скорости значит оставить энергию в теле после того, как перекрытие ушло. В
стопке этой энергии некуда деться, куча гудит и ползёт.

Поэтому коррекция решается во вторую, параллельную скорость (`pseudoLinear` /
`pseudoAngular`), которая двигает тело при интегрировании и выбрасывается. Вне
шага она ноль и частью состояния тела не является.

`maxCorrectionSpeed` важнее всего, когда тело появилось внутри геометрии: без
потолка первый же шаг выстреливает им через полкарты.

## character.hpp

```cpp
struct CharacterSettings {
    float width = 0.6f, height = 1.8f, eyeHeight = 1.62f;
    float walkSpeed = 4.3f, runSpeed = 5.9f;
    float jumpSpeed = 8.6f, gravity = 24.0f, terminalSpeed = 60.0f;
    float stepHeight = 1.05f;
    float airControl = 0.28f;
    float groundFriction = 0.02f, airFriction = 0.85f;

    // Вода
    float swimSpeed = 2.6f, swimUpSpeed = 3.4f, swimDownSpeed = 3.0f;
    float buoyancy = 0.94f, waterDrag = 0.02f, waterEntrySpeed = 9.0f;
    float swimControl = 0.62f, swimThreshold = 0.5f;
};

struct Character {
    Vec3  position;             // СТУПНИ: по центру в x и z, на полу в y
    Vec3  velocity;
    float yawDegrees, pitchDegrees;   // yaw 0 смотрит в -Z, как у сущности
    bool  onGround, hitWall, hitCeiling;

    float submersion;           // доля коробки в жидкости, 0..1
    bool  inWater, swimming, eyesUnderwater;
    BlockId fluid, eyeFluid;    // какая именно, у ног и у глаза

    Vec3 eye(const CharacterSettings&) const;
    Vec3 forward() const;         // куда смотрит
    Vec3 walkForward() const;     // то же, уложенное на землю
    Vec3 right() const;
};

void stepCharacter(Character&, const World&, const CharacterSettings&,
                   Vec3 wish, bool jump, bool run, float dt);
bool characterFits(const World&, const CharacterSettings&, Vec3 position);
float characterSubmersion(const World&, const CharacterSettings&, Vec3 position);
Vec3 dropToGround(const World&, const CharacterSettings&, Vec3 position,
                  float maxFall = 128.0f);
```

**Намеренно не твёрдое тело.** `RigidBody` — это то, чем владеет и что толкает
солвер; персонаж — это то, чем управляет человек, и хотят они противоположного.
У тела под солвером есть трение, отскок, опрокидывание и сон, и всё это игрок
ощущает как вязкость управления. Персонаж кинематический: он идёт куда сказано,
а столкновение только отнимает то, чего он не может получить.

Мир снова делает это лёгким случаем. Против решётки единичных кубов нет ни
меша, ни тонкого треугольника, ни двусмысленности в том, что считать
поверхностью: коробка двигается **по одной оси за раз**, и после каждого
движения выталкивается из ячеек, которые задела. Три развёртки, никакого
решателя.

`wish` — направление, которое просит игрок, в мировом пространстве и **не
обязательно единичное**: длина больше единицы зажимается, поэтому аналоговый
стик передаётся как есть.

`walkForward` существует ради одной вещи: ходьба с взглядом себе под ноги не
должна замедлять.

### Вода — не стена и не воздух

Как воздух — падаешь на дно озера на предельной скорости и выходишь по дну; как
стена — стоишь на поверхности. Жидкая ячейка не останавливает ничего **и** держит
то, что внутри, и это два разных факта об одном блоке: `fluid` рядом с
`solid` в `BlockDef`.

Всё остальное считается через одно число. `submersion` — доля высоты коробки в
жидкости, и мерится **послойно**: пловца интересует, насколько он глубоко, а
«вода ли на этой глубине» — вопрос про слой целиком. Поэтому тело, стоящее
наполовину на берегу и наполовину в озере, считается на той глубине, на которой
оно есть, а не на половине от неё — что и верно, вода над ним ровно такая.

Одно число, а не флаг, потому что в плавании всё — вопрос степени: брести — это
та же физика с меньшим коэффициентом, и контроллеру с булевым полем понадобился
бы порог на каждое использование вместо одного.

- **Подъёмная сила** — доля гравитации, чуть меньше единицы. Отпустишь всё —
  медленно тонешь. Больше единицы — тело выскакивает пробкой, и это читается как
  баг даже тем, кто не скажет, что не так.
- **Сопротивление** — доля скорости, сохраняемая за секунду, и применяется
  только к вертикали и к горизонтали **без ввода**. На управляемой горизонтали
  его нет намеренно: сопротивление против рулевого члена делает достигнутую
  скорость отношением двух темпов, и `swimSpeed` начал бы значить что-то другое.
- **Потолок скорости падения** тянется от `terminalSpeed` к `waterEntrySpeed` по
  мере погружения. Сопротивление само по себе не успевает: экспоненциальный
  спад с предельной скорости уносит на пятнадцать блоков вниз, то есть нырок в
  озеро кончается на дне — тот же баг, что и полное отсутствие воды, только
  медленнее. Сначала это был одноразовый зажим на шаге входа, и он **не
  срабатывал ни разу**: флаги пересчитываются в конце каждого шага, так что к
  моменту вопроса «был ли я в воде» ответ уже «я в ней». Потолок и чинит это, и
  честнее по смыслу — вода сопротивляется быстрому телу каждый шаг, а не только
  первый.
- **Тяга вверх и вниз** — целевая скорость, как ходьба, а не сила против
  сопротивления: нажатие вверх должно поднимать с предсказуемым темпом.
  Умножается на `submersion` **в квадрате**: линейно тяга почти не спадает у
  самой поверхности, и пловец всплывает, пока в воде не остаются одни щиколотки.
  В квадрате он замирает по грудь.
- **Прыжок остаётся прыжком**, пока под ногами есть опора, и порога для этого не
  нужно. Оттолкнуться от дна озера — обычный прыжок, у которого сопротивление
  забирает большую часть. `swimThreshold` только сообщает наружу, плывут сейчас
  или падают сквозь воду.
- **Из воды вылезают** тем же шагом в `stepHeight`, что и на лестнице, — просто
  разрешённым, когда под ногами ничего нет. Без этого берег для пловца стена: он
  тычется в него и никогда не поднимается.

Контроллеру всё равно, **какая** жидкость: вода и лава держат тело одинаково, и
потому делят каждое число выше. Всем остальным — нет: одна красит кадр синим,
другая убивает. Поэтому `fluid` и `eyeFluid` сообщают, какая именно, у ног и у
глаза, а не только что она есть. Игре с одним флагом пришлось бы гадать, и
некоторое время она гадала: голова в лаве красила кадр тем же спокойным синим,
что и голова в озере.

Замерено: падение с 43 блоков останавливается на 12-м из 17 (дно на 2-м);
отпущенный тонет со скоростью 0.32 блока/с; удерживая вверх, всплывает и
**стоит** на 15.96 с погружением 0.58 — то есть с головой наружу; ныряет на 6.3
блока за три секунды; плывёт со скоростью 2.6 против 4.3 пешком.

Гравитация 24 м/с², а не 9.81. Блок — метр поперёк, и при настоящей гравитации
падение на его высоту занимает заметно долго; ощущается как ходьба под водой.
`jumpSpeed` подобран так, чтобы взять блок и вернуться на него.

> **`stepHeight` — выбор, а не число игры.** Здесь 1.05, чуть больше блока; в
> Minecraft он 0.6, поэтому целый блок там прыгают, а шагом берут только плиты и
> ступени. Лестница из целых блоков — самое частое, что строят в воксельном
> мире, и необходимость подпрыгивать на каждой ступени есть разница между
> миром, по которому идёшь, и миром, с которым борешься. Ставится обратно в 0.6
> одной строкой.

`characterFits` и `dropToGround` открыты наружу, потому что нужны спавнеру:
уронить игрока в стену — единственный способ заставить исправный контроллер
выглядеть сломанным. `dropToGround` возвращает первую позицию на уровне
`position` или выше, где персонаж помещается.

## Воспроизводимость

При фиксированном шаге прогон побитово повторяем, и `test_physics` это требует:
та же сцена, тот же порядок добавления тел, то же число шагов — тот же ответ до
бита. Это не роскошь, а способ вообще отлаживать солвер: «разъехалось на сотом
шаге» имеет смысл только тогда, когда сотый шаг один и тот же.

Отсюда же правило про скрипт: он не источник случайности внутри шага. То же
требование, что `shot` предъявляет к [дублю](api-anim.md).

## Чего нет

- **Непрерывной проверки столкновений.** Шаг дискретный, и тело, проходящее за
  один шаг собственную толщину, пройдёт сквозь пол. Контроллера персонажа это
  не касается: он идёт развёртками по осям, и `test_physics` роняет его с
  четырёхсот блоков.
- **Неоднородной плотности.** См. врезку в `collider.hpp` выше.
- **Форм, кроме коробок.** Для вокселей это не приближение, а точное описание, и
  сфера с капсулой сюда не встают — но и не нужны.
- **Встречи персонажа с телами.** `stepCharacter` видит только `World`. Ящик
  игрока не толкнёт, и игрок ящик не сдвинет: они пока не знают друг о друге.
  Физган это обходит, а не решает: он двигает тело, а не персонажа.
- **Инкрементальной широкой фазы.** Границы тел пересобираются каждый шаг.
- **Поколений у индексов тел.** Слот выдаётся заново, поэтому индекс удалённого
  тела молча называет следующее. Соль на ключе импульсов чинит единственное
  место, где это ломало **физику**; всё остальное — договор, который держит
  вызывающий. Настоящий ответ — упакованный дескриптор «слот + поколение», и он
  расходится по `Constraint`, по скриптовым привязкам и по всему, что хранит
  `int`.
- **Жидкостей для тел.** Вода действует только на персонажа: ящик, брошенный в
  озеро, тонет как в воздухе. Это тот же `BlockDef::fluid`, только применённый в
  `collideBodyWithWorld` и в шаге — выталкивающая сила по объёму погружённых
  коробок, — но всплывающие тела хочется мерить, а не приписывать.
- **Непрерывного манифолда.** Контакт существует, только пока есть
  проникновение: соприкасающиеся ровно коробки не дают ни одной точки, и пара
  подрагивает между «есть» и «нет», удерживаемая допуском. Спекулятивный запас
  убрал бы и это.
