# Установка и сборка

[← README](../README.ru.md) · [in English](install.md)

Пока только Windows; внизу [про Linux](#linux) — что именно мешает и что для
этого нужно сделать.

Коротко, если инструменты уже стоят:

```
git clone https://github.com/Hiro-zzz/BlockyEngine.git
cd BlockyEngine
build.cmd release
build\RelWithDebInfo\konstruct.exe
```

---

## Что нужно

**Visual Studio — или только его Build Tools.** Build Tools бесплатны, и их
достаточно: сама IDE здесь не используется. Взять то или другое можно на
[visualstudio.microsoft.com/downloads](https://visualstudio.microsoft.com/downloads/);
Build Tools лежат внизу страницы, в разделе *Tools for Visual Studio*.

В установщике отметьте **Разработка классических приложений на C++** (*Desktop
development with C++*). Это исчерпывающий ответ, и большинству стоит поступить
именно так.

Если хочется поставить как можно меньше — хватит трёх компонентов:

| Компонент | Зачем |
|---|---|
| MSVC v145 (или новее) — средства сборки x64/x86 | Компилятор. Нужен **14.5 или новее**: код на C++20 и использует то, что более ранние наборы понимают неверно |
| Windows 11 SDK | Заголовки Win32 и OpenGL |
| Средства CMake для Windows (C++ CMake tools) | Приносит CMake и Ninja. `build.cmd` берёт именно их, а не то, что лежит в PATH |

И больше ничего. Ни отдельного CMake, ни Ninja, ни менеджера пакетов, ни
зависимостей, которые надо докачать, — их у движка нет.

**Машина, на которой всё это проверено** — как ориентир, а не как требование:
MSVC 14.50.35717, Windows SDK 10.0.26100, вложенные CMake 4.2.3 и Ninja 1.12.1,
Windows 11.

## Получить исходники

```
git clone https://github.com/Hiro-zzz/BlockyEngine.git
cd BlockyEngine
```

Клон весит около пятнадцати мегабайт, большая часть — витрина в
`docs/gallery/`. Подмодулей нет, при сборке ничего не скачивается.

## Сборка

```
build.cmd release
```

Это всё. Скрипт сам находит Visual Studio, поднимает окружение x64,
конфигурирует через CMake и Ninja и собирает всё: движок статической
библиотекой, сорок три сцены отдельными исполняемыми файлами и игру одним.

| Команда | Что делает |
|---|---|
| `build.cmd` | Сконфигурировать при необходимости и собрать Debug |
| `build.cmd release` | Собрать RelWithDebInfo — **только он годится для рендера** |
| `build.cmd run <имя>` | Собрать и запустить `scenes/<имя>.cpp` из корня проекта |
| `build.cmd clean` | Стереть каталог `build/` |

Debug трассирует примерно в двадцать раз медленнее. Он для того, чтобы пройтись
отладчиком по солверу, а не чтобы получить картинку.

Первая сборка компилирует всё и занимает несколько минут; дальше Ninja
пересобирает только изменившееся. Добавление или удаление файла в `scenes/`,
`engine/` или `game/` само перезапускает CMake — глоб-выражения объявлены
`CONFIGURE_DEPENDS`, поэтому новая сцена становится исполняемым файлом без
единой правки где бы то ни было.

### Если Visual Studio лежит не там, где обычно

`build.cmd` спрашивает `vswhere` — инструмент, который Microsoft выпустила
ровно для этого вопроса и кладёт рядом с каждой Visual Studio начиная с 2017-й,
— а если его нет, перебирает обычные каталоги. Если ваша установка не находится
ни так, ни так, скажите прямо:

```
set "BLOCKY_VSROOT=D:\VS\BuildTools"
build.cmd release
```

### Аргументы

`build.cmd` их не пробрасывает. Запускайте экземпляр напрямую, если сцене нужны
аргументы:

```
build\RelWithDebInfo\scenes\scene_diorama.exe draft
```

## Что-нибудь запустить

**Игра.**

```
build\RelWithDebInfo\konstruct.exe
```

Открывается меню поверх настоящего, медленно поворачивающегося мира.
`konstruct map=be_construct` минует меню и высаживает на стройплощадке,
`konstruct physgun` начинает с инструментом в руках. Полный список аргументов —
в [README](../README.ru.md#игра).

**Кадр.** Каждый файл в `scenes/` — свой исполняемый файл с именем
`scene_<файл>`. Пишут они в `out/` относительно того места, откуда запущены,
поэтому запускать надо из корня проекта:

```
build.cmd release run cornell
build\RelWithDebInfo\scenes\scene_diorama.exe draft
```

`draft` принимает большинство из них: уменьшенный быстрый прогон, чтобы
оценить свет до того, как считать всерьёз.

**Тесты.** Семнадцать наборов, каждый — обычная сцена, возвращающая ненулевой
код при провале:

```powershell
foreach ($t in @("test_raycast","test_zip","test_assets","test_entity","test_gl",
                 "test_gpu","test_procgen","test_sprite","test_prop","test_rig",
                 "test_face","test_anim","test_video","test_chunks","test_physics",
                 "test_script","hello")) {
    & ".\build\RelWithDebInfo\scenes\scene_$t.exe"
    if ($LASTEXITCODE -ne 0) { Write-Output "FAILED: $t" }
}
```

`test_zip` и `test_assets` требуют установленного Minecraft и без него
сообщают, что пропускают себя, а не падают. Что покрывает каждый набор —
в [testing.md](testing.md).

## Необязательное: ассеты Minecraft

**Ничего здесь их не требует.** Текстуры блоков генерируются кодом, персонажи
рисуются кодом, у шрифта есть встроенный запасной вариант. Все сцены рендерятся
и игра играется, когда не установлено ничего.

Установленная игра добавляет настоящий рисунок. Если она есть, движок сам
находит клиентский `.jar` — `AssetSource::findClientJar()` смотрит в `%APPDATA%`
официальный лаунчер, TLauncher и Prism и берёт самую новую найденную версию.
Ничего не распаковывается: `.jar` читается там, где лежит.

Ресурспак работает так же — передайте `.zip` в `AssetSource::open`.

Без установленной игры `scene_textured_island` рендерится плоской палитрой,
`test_zip` и `test_assets` пропускают себя, а игра генерирует свои текстуры и
разницы не замечает.

## Видеокарта

Трассировщику на процессоре не нужно ничего.

Вьюпорту, игре и трассировщику на карте нужен **OpenGL 4.6 core**. Это любая
дискретная карта примерно с 2015 года и встроенная графика Intel того же
времени — но именно свежие драйверы, а не те, что Windows ставит сама.
`scene_test_gl` отвечает на вопрос прямо: создаёт контекст 4.6, проверяет
полноту таблицы функций и печатает, что получилось.

Пути через Vulkan или D3D нет и не планируется: компьют-шейдеры, из которых
сделан трассировщик на карте, — это ядро OpenGL 4.3, а контекст всё равно уже
открыт ради вьюпорта.

## Когда не работает

**`no Visual Studio with the C++ toolset was found`** — либо она не
установлена, либо при установке не отмечали C++. Запустите Visual Studio
Installer, нажмите *Изменить* и отметьте **Разработка классических приложений
на C++**. Если установка лежит в необычном месте — задайте `BLOCKY_VSROOT`, как
выше.

**`found ... but no cmake in it`** — Visual Studio есть, но без компонента
**Средства CMake для Windows**. Лечится там же: *Изменить*, отметить.

**`vcvars64 failed`** — обычно установка только 32-битная либо без
инструментов x64. Отмечать надо компонент, в названии которого есть *x64/x86
build tools*.

**Окно открывается чёрным или падает `test_gl`.** Драйверы видеокарты. Карта
обязана сообщать OpenGL 4.6; запустите `scene_test_gl`, и он напечатает, что
получил на самом деле.

**Кириллица и прочее не-ASCII в пути.** Поддерживается сознательно — сам этот
репозиторий разрабатывается в таком пути, — но только потому, что каждая
файловая операция идёт через `readFileBytes` / `writeFileBytes`, которые сперва
переводят путь в UTF-16. Узкие функции CRT такие пути калечат, так что если
добавляете код, открывающий файл, берите эти две, а не `fopen`.

**Чтобы запустить собранное, ставить не нужно ничего.** CRT слинкована
статически, поэтому исполняемые файлы импортируют только `OPENGL32`, `USER32`,
`GDI32` и `KERNEL32` — всё это часть Windows. Никаких распространяемых пакетов,
и собранную сцену можно скопировать на другую машину одним файлом.

## Linux

**Пока не поддерживается.** Хочется и планируется; ниже — где это на самом деле
стоит, потому что «будет позже» само по себе не говорит ничего о том, насколько
позже.

Почти весь движок — обычный переносимый C++20, и портировать в нём нечего:
трассировщик, солвер физики, кодеки PNG и ZIP, энкодер H.264, скриптовый язык,
все `scenes/` целиком. В `engine/core/file.cpp` POSIX-ветка уже написана рядом
с Win32-ветвью.

По-настоящему привязаны к Windows две вещи, и это два файла:

| Файл | Что это | Что понадобится для Linux |
|---|---|---|
| `engine/platform/window.cpp` | Окно и сырой ввод мыши на Win32 | Тот же интерфейс `Window` поверх X11 или Wayland |
| `engine/render/gl/gl_loader.cpp` | Загрузка функций через WGL | Та же таблица, заполненная через GLX или EGL |

Плюс `build.cmd` — это батник; сам CMake уже нейтрален, если не считать одного
блока `if(MSVC)` с флагами компилятора.

То есть форма порта понятна: по второй реализации за каждым из этих двух
интерфейсов и shell-скрипт или пресет CMake рядом с `.cmd`. Чего **нет** — так
это того, чтобы хоть что-то из этого было скомпилировано под Linux хотя бы
раз: переносимость выше — это то, как код написан, а не то, что подтвердил
компилятор. Первая же попытка наверняка вскроет десяток мелочей, как бывает
всегда.

А пока честная сводка такая: Windows 10 или 11, x64.
