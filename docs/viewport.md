# Вьюпорт

[← README](../README.ru.md)

OpenGL 4.6 core на голом Win32 + WGL, со своим загрузчиком функций.

Задача вьюпорта — **не** рендерить. Рендерит path tracer. Задача вьюпорта —
дать встать где-то, посмотреть на что-то и получить эти числа обратно кодом.
Всё остальное подчинено этому: ни теней, ни отражений, ровно столько
затенения, чтобы читалась форма.

С тех пор у него появилась вторая работа, которой он не искал: это ещё и окно,
в котором идёт мир. `scene_live` и [игра](../README.md#игра) — это тот же
`runViewport` с [хук-швом](#шов-превращающий-смотрелку-в-хост) и камерой от
хоста. Новой подсистемой это не стало: три поля в настройках, и всё, что
вьюпорт умеет про меняющийся мир, идёт от них.

---

## Запуск

```
scene_viewport                        облёт острова
scene_viewport cast                   облёт сцены с персонажами
scene_viewport snapshot out/x.png     один кадр в файл, без окна
scene_viewport snapshot out/x.png trace   ... и тот же ракурс трассировщиком
```

Последняя форма — приёмочный тест: `out/x.png` и `out/x_traced.png` должны
совпадать по кадрированию и материалам, а расходиться только там, где у
трассировщика есть тени, преломление и GI.

Тот же вьюпорт под хостом — это уже не облёт, а идущий мир:

```
scene_live                            физика идёт, скрипт перечитывается
konstruct                           ходьба от первого лица
konstruct snapshot out/g.png frames=120   идущий мир в файл, без окна
```

## Управление

| Клавиша | Действие |
|---|---|
| Правая кнопка мыши | Осмотреться |
| `W` `A` `S` `D` | Движение |
| `Space` / `Shift` | Вверх / вниз |
| Колесо | Скорость движения |
| `F` | Напечатать камеру готовым C++ |
| `P` | Снимок в `out/viewport.png` |
| `Esc` | Выход |

`F` печатает:

```cpp
scene.camera.projection = Camera::Projection::Perspective;
scene.camera.fovY = radians(50.0f);
scene.camera.lookAt({52.317f, 34.008f, 52.114f}, {51.640f, 33.716f, 51.437f});
```

Скопировал — вставил в трассируемую сцену. Это и есть рабочий цикл, ради
которого вьюпорт делался. Камера печатается и при выходе, так что случайно
закрытое окно не теряет найденный ракурс.

## API

```cpp
int runViewport(Scene& scene, const ViewportSettings& settings);
```

| Поле | По умолчанию | Смысл |
|---|---|---|
| `width` / `height` | `1280 × 720` | Размер клиентской области |
| `title` | — | Заголовок окна |
| `vsync` | `true` | Ждать развёртку |
| `msaa` | `4` | Сглаживание; 0 — выключить |
| `moveSpeed` | `8.0` | Блоков в секунду, дальше крутится колесом |
| `mouseSensitivity` | `0.12` | Градусов на пиксель |
| `exposure` | `1.0` | Экспозиция предпросмотра |
| `snapshotPath` | пусто | Если задано — один кадр в файл, окно не показывается |
| `snapshotFrames` | `1` | Сколько кадров прогнать до снимка |
| `onFrame` | пусто | Хук раз в кадр; `false` завершает цикл |
| `hostCamera` | `false` | Камеру ведёт хост, а не облёт |
| `statusText` | `nullptr` | Строка, дописываемая к заголовку окна |
| `onOverlay` | пусто | Хук интерфейса, поверх готового кадра |
| `snapshotOverlay` | `false` | Рисовать интерфейс и в снимке |
| `freeCursor` | `nullptr` | Указатель на флаг хоста: пока `true`, курсор не захватывается |
| `hostEscape` | `false` | Оставить `Esc` хосту вместо выхода из цикла |
| `effects` | `nullptr` | Пост-обработка: cel, контур, bloom, грейдинг, виньетка |

Камера, до которой долетел пользователь, печатается при выходе.

**Сцена принимается по неконстантной ссылке и может меняться — но только из
`onFrame`.** Сам вьюпорт в ней не трогает ничего.

## Шов, превращающий смотрелку в хост

Три поля выше — это то, из-за чего вьюпорт перестал быть только смотрелкой, и
на них построены `scene_live` и [игра](../README.md#игра).

```cpp
ViewportSettings viewport;
viewport.hostCamera = true;          // камеру ведём мы
viewport.statusText = &status;
viewport.onFrame = [&](const ViewportFrame& frame) {
    if (frame.input) aimPlayer(player, *frame.input, frame.dt);
    physics.step(scene.world, kStep);
    scene.camera = playerCamera(player, 74.0f, scene.camera.aspect);
    return true;                     // false завершил бы цикл
};
return runViewport(scene, viewport);
```

`onFrame` зовётся раз в кадр **до** отрисовки, и сцена под ним свободна
меняться. Всё, что вьюпорт делает с меняющимся миром — перемеширование только
тех чанков, чей штамп сдвинулся, перечитывание размещений пропов, — существует
из-за этого шва, и ничему выше не нужно знать, откуда пришли изменения: из
физики, из скрипта или из нажатия клавиши.

`ViewportFrame` несёт `dt` (уже зажатый: затык не имеет права ничего
телепортировать), `time` от первого кадра, `index` и `input`.

> `input` — это **само окно**, а не вторая абстракция ввода. Игре нужно от него
> больше, чем вьюпорт мог бы угадать, и промежуточная структура означала бы
> добавлять в неё поле каждый раз, когда игре понадобилась ещё одна клавиша.
>
> В режиме снимка `input` равен `nullptr`: окна нет и читать нечего. Хост
> обязан это учесть — и заодно шагать фиксированной величиной вместо часов, что
> и делает снимок воспроизводимым. Отсюда же `snapshotFrames`: у первого кадра
> `dt` микросекундный, поэтому хост с фиксированным шагом к моменту снимка не
> сдвинется вообще, и всё, что доказывает **изменение**, требует больше одного
> кадра.

`hostCamera` не удаляет облётную камеру, а ставит её в сторону: найти ракурс и
вставить его в сцену — по-прежнему то, **зачем** вьюпорт есть, и построенная на
нём игра должна уметь вернуть управление обратно.

## Пост-проход

Раньше каждый шейдер доводил свой фрагмент до конца: затенить, выставить
экспозицию, прогнать через ACES, закодировать в sRGB. Для программы, которая
только показывает блоки, это верно — и неверно, как только что-то должно
посмотреть на **готовую картинку**: контуру нужен соседний пиксель, а bloom'у
нужно знать, какие пиксели были яркими.

Поэтому мир рисуется в offscreen-цель в **линейном свете**, а один проход в
конце смотрит. Ровно тот порядок, что у процессорных рендереров: `Image`
линейный, `post/` его фильтрует, `tonemap` срабатывает один раз в самом конце.
Вьюпорт теперь согласен с ними не только про кривую, но и про порядок действий.

```
геометрия ──▶ RenderTarget ──▶ bright ──▶ blur×2 ──▶ composite ──▶ окно
              RGBA16F цвет     половинный размер     контур, bloom,
              RGBA8 нормаль                          грейдинг, виньетка,
              depth24                                ACES, sRGB
```

**Две половины цели.** Цвет — `RGBA16F`, потому что bloom ищет значения выше
единицы, а восемь бит sRGB их выбросили по построению. Нормали лежат вторым
вложением, а не восстанавливаются из глубины: восстановление даёт нормаль
**градиента глубины**, что на воксельном мире одно и то же ровно до плоского
пола под скользящим углом — там он читается как склон, и контур проводит линию
поперёк пустого места.

`ViewportEffects` — ручки этого прохода, и передаются они указателем по той же
причине, что `statusText`: хост, у которого вид переключается клавишей, обязан
уметь поменять его после того, как настройки уже отданы.

> **Проход не опционален.** Геометрические шейдеры теперь пишут линейный свет и
> больше ничего, поэтому без прохода, который его тонмапит, картинки нет —
> только неограниченные значения, зажатые восьмибитным окном. Полуработающий
> запасной путь означал бы второй путь освещения, который надо держать в
> согласии с первым, — устройство, которое этот движок отвергает везде.

### Среда: тон и дымка

```cpp
Vec3  tint{1, 1, 1};       // на что умножается кадр
float fogDensity = 0.0f;   // на блок; 0 выключает
Vec3  fogColour;
```

Обе ручки выключены по умолчанию и существуют ради одного случая — когда
камера **внутри** чего-то. Голова под водой — это не грейдинг, а среда, и среда
делает ровно две вещи: поглощает (тон) и рассеивает (дымка).

Применяются они здесь, а не в геометрическом проходе, по тому же шву, что и
контур: буфер глубины уже лежит в этом шейдере, а альтернатива — рассказать про
жидкость каждому вызову отрисовки во вьюпорте. Дальность неба при этом
оказывается ровно тем, что нужно: под водой неба нет, есть ещё вода.

Трассировщику ничего этого не нужно. Там вода — настоящая среда с настоящим
коэффициентом поглощения, и луч, вошедший в неё, знает об этом сам.

### У cel два шва и здесь

**Ступени** накладываются при затенении, в `shade()`. Квантовать надо
освещённость, а к моменту готового кадра она уже умножена на альбедо: полосить
цвет значит полосить текстуру вместе со светом, и каменный блок выйдет в
четырёх оттенках серого, не имеющих отношения к тому, где солнце. Отличие от
трассировщика в том, что у растеризованного кадра ровно один отскок, поэтому
здесь это **и есть** итоговая освещённость, а не один вклад в неё.

**Контур** накладывается в пост-проходе, потому что краю нужны соседи. Берётся
он из глубины и нормалей: фильтр по изображению обвёл бы заодно каждую границу
текстуры, то есть каждую грань блока, — вышла бы раскраска.

Допуск по глубине **относительный**. Фиксированный рисует каждую дальнюю
поверхность одной сплошной линией, потому что шаг в один пиксель охватывает тем
больше мира, чем дальше он от камеры.

> На воксельном мире полосы делают меньше, чем кажется: у грани постоянная
> нормаль, значит и постоянная освещённость, и квантовать там почти нечего.
> Видимую часть работы делают контур и ступени на AO. Это свойство мира из
> кубов, а не недоделка — и `INK` существует, чтобы показать контур отдельно.

## Интерфейс

У вьюпорта не было никакого интерфейса, и для инструмента подбора ракурса это
верно: заголовка окна хватает. Игре нужны меню, прицел и ряд блоков, а ни одно
из трёх не выражается геометрией в мире.

`engine/render/gl/overlay.hpp` — плоские квады и текст **в пикселях от левого
верхнего угла окна**, потому что это единственная система координат, которую
можно держать в голове, раскладывая меню. NDC положили бы начало в центр,
перевернули вертикаль и поставили каждый размер в зависимость от соотношения
сторон.

```cpp
viewport.onOverlay = [&](Overlay& ui) {
    ui.rect(x, y, w, h, rgb8(14, 17, 23, 0.82f));
    ui.textShadowed(x + 16, y + 12, "SINGLEPLAYER", 3.0f, rgb8(255, 198, 92));
};
```

Три вещи в нём стоит знать:

- **Один вызов отрисовки.** Квады копятся между `begin` и `end` и уходят на
  карту один раз. Сплошные и глифовые лежат в одном буфере и различаются
  флагом в вершине: два прохода означали бы либо два вызова, либо правило
  порядка между ними, а панель, нарисованная после текста, который она
  закрывает, — это баг, который никто не любит искать.
- **Он рисуется после тональной кривой.** Это интерфейс, а не свет. Цвет,
  выбранный здесь, — цвет, который окажется на экране; прогнать меню через
  ACES значило бы получить не тот, что выбирали.
- **Из шрифта берётся только покрытие.** Чернила белые, а лист загружен как
  sRGB, поэтому брать оттуда цвет значило бы просить драйвер линеаризовать
  значение, которое мы тут же пишем как есть. Альфа — это альфа в любой
  кодировке.

> **Ловушка, стоившая одной итерации.** `Font::Glyph::uvMax.x` уже обрезан по
> ширине чернил, а `uvMax.y` — нет. Квад глифа поэтому шириной **в чернила** и
> высотой в целую клетку. Нарисовать клетку целиком — ошибка, которая не
> выглядит ошибкой: перо шагает на чернила плюс колонку, поэтому клетка
> наезжает на следующий глиф, и текст читается как проблема шрифта, а не как
> проблема раскладки.

Курсор и `Esc` — два обещания, а не два флага. Меню требует указателя, поэтому
`freeCursor` снимает захват; меню требует `Esc`, поэтому `hostEscape` отдаёт
клавишу. Второе выключено по умолчанию нарочно: окно, которое нельзя закрыть,
— не любезность, и хост, включающий флаг, обещает, что выход есть.

## Как устроено

### Окно

`engine/platform/window.hpp` — минимальный Win32: создать окно, прокачать
сообщения и рассказать, что сделали клавиатура и мышь с прошлого кадра.

```cpp
bool create(title, width, height, error);
void show();
bool pumpEvents();          // false, когда окно пора закрывать

bool  keyDown(int virtualKey) const;      // удерживается сейчас
bool  keyPressed(int virtualKey) const;   // нажата в этом кадре, по фронту
bool  mouseRightDown() const;
Vec2  mouseDelta() const;
float wheelDelta() const;
void  setCursorCaptured(bool);
```

Коды клавиш — виртуальные коды Win32; те, что нужны вьюпорту, названы в
`namespace key`, чтобы сцене не включать `windows.h`.

### Контекст

Классический тупик: `SetPixelFormat` можно вызвать для окна ровно один раз, а
современный формат выбирается через `wglChoosePixelFormatARB`, которому нужен
уже живой контекст.

Поэтому загрузчик поднимает **временное окно** с legacy-контекстом, забирает
из него два указателя расширений и уничтожает. На настоящем окне формат
ставится сразу правильный.

```cpp
gl::ContextSettings settings;
settings.samples = 4;
settings.debug = false;

void* context = nullptr;
gl::createContext(window.deviceContext(), settings, &context, &error);
```

Все функции GL лежат в одной таблице `blocky::gl` без префикса `gl` —
`gl::Clear`, `gl::DrawArrays`, `gl::UseProgram`. Включая GL 1.1, которые
экспортирует `opengl32.lib`: смешение заголовка версии 1.1 с указателями
времени выполнения приглашает устаревшие прототипы.

`wglGetProcAddress` на некоторых драйверах возвращает 1/2/3/−1 вместо нуля,
поэтому загрузчик откатывается на `GetProcAddress` по `opengl32.dll`.

### Ресурсы GPU

> Трассировщик на видеокарте строит **свой** массив текстур блоков и не берёт
> этот: у вьюпорта запечён превью-цвет воды, восемь бит sRGB и мипы, и всё три
> ему мешают. Почему именно — в [api-gpu.md](api-gpu.md#block_textures_gpuhpp).

`engine/render/gl/gl_resources.hpp`:

- `ShaderProgram` — компиляция и линковка с внятными сообщениями.
- `GpuMesh` / `MeshData` — геометрия мира, 20 байт на вершину: позиция float,
  а слой текстуры, нормаль, AO и угол грани упакованы.
- `GpuSkinMesh` / `SkinMeshData` — геометрия сущности; координаты адресуют скин
  напрямую, поэтому он биндится обычной 2D-текстурой.
- `GlBlockTextureArray` — **массив** текстур, не атлас.
- `GlTexture2D` — скин.

```cpp
void buildWorldMesh(const World&, MeshData& opaque, MeshData& translucent);
void buildEntityMesh(const Entity&, SkinMeshData& out);
```

Грань рисуется, когда сосед пропускает свет, — то же правило, что в игре. Две
соприкасающиеся воды прячут поверхность между собой.

**Массив текстур, а не атлас.** Все текстуры блоков 16×16, значит ложатся
слоями одинакового размера: ни упаковки, ни пересчёта UV, ни подтекания на
границах мип-уровней. Слой — `blockId * 6 + face`, тинт и наложение запечены
при сборке через тот же `sampleAlbedo`, что использует трассировщик, поэтому
цвет совпадает с CPU по построению.

Прозрачные блоки текстуры не имеют — они предпросматриваются цветом, который
дала бы среда после нескольких блоков пути.

### Шейдеры

Небо, блоки и скины делят одну общую часть: та же аналитическая модель неба,
та же кривая ACES, то же кодирование sRGB, что у CPU-рендереров, — чтобы
вьюпорт и трассированный кадр сходились по тону.

sRGB кодируется **в шейдере явно**, а не через `GL_FRAMEBUFFER_SRGB`:
стандартный фреймбуфер не обязан быть sRGB-совместимым, и расчёт на флаг мог
бы тихо ничего не делать.

Небо рисуется одним негабаритным треугольником без вершинного буфера, с
выключенным тестом глубины — отключение теста заодно отключает и запись, так
что фон никогда не перекрывает мир.

Прозрачным средам достаётся 12% солнечного вклада: вода — среда, а не
диффузная поверхность, и полноценный блик превращает её в молоко.

## Мышь

Обзор берётся из **raw input**, а не из позиции курсора.

Очевидный способ — прочитать позицию, вычесть предыдущую, вернуть курсор в
центр — здесь и был, и он тихо неверен. Windows склеивает сообщения о движении,
поэтому синтетическое перемещение от возврата в центр и настоящее движение
игрока могут прийти одним сообщением или в другом порядке; флаг «пропустить то,
что мы сделали сами» тогда съедает настоящее. При центрировании раз за перетаскивание
это незаметно настолько, что с летающей камерой можно жить. При центрировании
каждый кадр — а именно это нужно захваченному курсору — половина ввода пропадает.

Raw input отдаёт собственные относительные отсчёты устройства: ничего не
вычитается, ничего не синтезируется, позиция курсора перестаёт участвовать в
ответе. Возврат в центр остался, но только чтобы указатель не ушёл из окна.

Захват отпускается при потере фокуса и при закрытии окна: окно, которое тянет
указатель к себе, пока вы работаете в другом, — это не игра.

## Чего нет

- **Теней.** Для расстановки камеры хватает AO и `N·L`.
- **Отсечения по пирамиде видимости.** На 49 тысячах треугольников это не
  важно, на большом мире понадобится.
- **Приоритета перестроения.** Меш **перестраивается** — это делает
  `ChunkMeshCache`, и он существует ровно потому, что мир перестал быть
  статичным: `World` штампует тронутые чанки глобальным счётчиком, кэш помнит
  штамп, на котором меширил каждый, и заново собирает только разошедшиеся.
  Стороны при этом не договариваются — поэтому рядом без единой правки встанет
  такой же кэш физики или света. Чего нет — это **выбора**, какие из
  просроченных чанков возьмёт урезанный бюджет: сейчас порядок хеша, а игре
  нужны ближайшие к камере.
Позы вьюпорт показывает: меширование сущностей вызывает тот же
`Skeleton::resolve`, что и трассировщик, поэтому согнутый локоть выглядит
одинаково в предпросмотре и в кадре.

- **Спрайтов.** `buildSpriteMesh` нет: частицы и парящий текст видны только
  в трассировке. Для поиска ракурса это не мешает, но помни, что кадр во
  вьюпорте беднее финального. Пропы рисуются — своим шейдером, цветом из
  палитры модели, по той же матрице `PropSet::Flat::toWorld`, которую обходит
  трассировщик.
- **Проигрывания дубля.** Вьюпорт ищет ракурс для одного кадра. Анимация —
  цикл вокруг трассировщика, и крутить его здесь значило бы рендерить
  предпросмотр ценой финального кадра, только без GI. Позу текущего кадра он
  показывает: тот же `resolve`, что у трассировщика.
