---

Второй трассировщик. Тот же интегратор, что в `render/trace`, только считает
его видеокарта: те же четыре лепестка, та же явная выборка солнца и светящихся
граней, те же преломляющие среды с поглощением по Бугеру — Ламберту, та же
русская рулетка и тот же зажим светлячков.

Никакой новой зависимости это не стоило. Компьют-шейдеры и storage-буферы —
ядро OpenGL 4.3, а контекст 4.6 core вьюпорт открывает своим загрузчиком с
самого начала. Ни Vulkan, ни CUDA, ни OptiX.

**CPU-путь остаётся и никуда не денется.** Он здесь эталон — ровно в том
смысле, в каком ffmpeg служит эталоном видеокодеку: вещь, согласная сама с
собой, не доказывает ничего.

---

## Из чего состоит

| Файл | Что в нём |
|---|---|
| `raycast_gpu.hpp` | Обход вокселей и упаковка мира. Шаг первый: тот же вопрос, что у `raycast()`, и ничего сверх |
| `pathtrace_gpu.hpp` | Мегаядро: весь путь луча в одном шейдере. Только воксельный мир |
| `wavefront_gpu.hpp` | Тот же трассировщик очередями по стадиям. Умеет всё: текстуры, сущности, спрайты, пропы |
| `block_textures_gpu.hpp` | Массив текстур блоков для трассировщика — свой, не вьюпортовый |
| `entities_gpu.hpp` | Уплощённые коробки сущностей и массив скинов |
| `offgrid_gpu.hpp` | Спрайты и пропы: то, что живёт вне решётки, вместе со своим BVH |
| `denoise_gpu.hpp` | A-trous по AOV. Стоит отдельно и подменяет CPU-фильтр один в один |

## Как этим рендерить

Нужен живой контекст, значит нужно окно — но показывать его никто не обязывает.

```cpp
#include "engine/platform/window.hpp"
#include "engine/render/gl/gl_loader.hpp"
#include "engine/render/gpu/denoise_gpu.hpp"
#include "engine/render/gpu/wavefront_gpu.hpp"

Window window;
window.create("gpu", 320, 200, &error);        // окно не показывается

gl::ContextSettings ctx;
ctx.samples = 0;
void* context = nullptr;
gl::createContext(window.deviceContext(), ctx, &context, &error);

gpu::WavefrontTracer wave;
wave.build(&error);                            // компиляция стадий
wave.upload(scene, &error);                    // мир, палитра, свет, каст

Image frame;
RenderTargets targets;
gpu::WavefrontStats stats;
wave.render(scene, settings, frame, &targets, &stats, &error);

gpu::Denoiser denoiser;
denoiser.build(&error);
Image filtered;
denoiser.run(targets, denoiseSettings, filtered, &error);
```

`PathSettings` — тот же, что у `renderPath`: разрешение, спп, отскоки, сид.
`RenderTargets` заполняются теми же четырьмя буферами (цвет, альбедо, нормаль,
глубина), поэтому весь пост — шумоподавитель, cel, bloom, грейдинг — работает
дальше без единой правки.

## raycast_gpu.hpp

Шаг первый и намеренно только он: какой блок задел луч и какой гранью. Ни
затенения, ни отскоков.

```cpp
PackedWorld packWorld(const World&);

class Raycaster {
    bool build(std::string* error = nullptr);
    bool upload(const PackedWorld&, std::string* error = nullptr);
    bool trace(const std::vector<GpuRay>& rays, std::vector<GpuHit>& hits, float maxDistance,
               BlockId passThrough = block::Air, bool opaqueOnly = false,
               std::string* error = nullptr);

    double lastUploadSeconds() const;      // раздельно — см. ниже
    double lastDispatchSeconds() const;
    double lastReadbackSeconds() const;
};
```

**Хеш-карта — единственное, что не переезжает.** На CPU мир это хеш-карта
плотных чанков 16³, и сетка чанков заодно служит ускоряющей структурой. На GPU
её место занимает **плотная** индексная сетка по габаритам чанков мира: номер
слота или −1. Сцены этого движка ограничены и внутри своих границ в основном
заполнены — площадка фильма это десятки чанков в поперечнике, — поэтому плотный
внешний уровень стоит килобайты и превращает поиск по хешу в одно чтение
массива. Двухуровневый DDA под ним тот же самый и ходит по тем же ячейкам в том
же порядке.

Время намеренно разложено на три: для партии лучей, отданной с CPU, интересна
**шина**, а не обход. Один общий итог это прячет полностью — и именно такое
измерение определило форму шага второго.

## pathtrace_gpu.hpp

Мегаядро: генерация луча, весь цикл отскоков и накопление — в одном шейдере,
один поток на путь.

```cpp
class PathTracer {
    bool build(std::string* error = nullptr);
    bool upload(const Scene&, std::string* error = nullptr);       // мир, палитра, свет
    bool render(const Scene&, const PathSettings&, Image& out,
                RenderTargets* aovs = nullptr, TraceStats* stats = nullptr,
                std::string* error = nullptr);

    int samplesPerBatch = 0;   // 0 — выбрать по числу пикселей
};
```

Умеет **только воксельный мир**: ни сущностей, ни спрайтов, ни пропов, ни
текстур блоков. Это не заготовка под будущее, а честная граница шага второго.

Через шину не ходит ничего, кроме готовой картинки: камерные лучи рождаются на
GPU, весь путь считается там же, буфер накопления возвращается один раз в конце.
Шаг первый измерил обход в десятки раз быстрее CPU — и тут же измерил, как три
четверти этого выигрыша съедает шина, если гонять лучи туда и попадания обратно
на каждом отскоке.

**Почему рендер идёт порциями.** Windows убивает ядро, считающее дольше пары
секунд, и перезапускает драйвер под ним. Кадр 1280×720 на 64 спп в один заход —
далеко за этой чертой, поэтому сэмплы раздаются партиями с накоплением в
постоянный буфер. Оттуда же берётся индикатор прогресса, и стоит это ноль:
дробление живёт на хосте.

`GpuMaterial` держит `topTint` отдельным полем. Трава коричневая на пяти гранях
и зелёная на шестой, CPU разбирается с этим в `surfaceAlbedo`, и без такого же
поля здесь GPU-кадр вернулся с коричневым газоном — ровно то, ради чего сверка
и заводилась.

## wavefront_gpu.hpp

Тот же трассировщик, но волной. Каждая стадия — своё маленькое ядро:

```
generate   по камерному лучу на пиксель, все пути живы
extend     трассировать активные лучи по миру
shade      выпустить теневые лучи, сэмплировать bsdf, оставить выживших
shadow     трассировать теневые лучи и добавить то, что дошло
resolve    свернуть завершившиеся пути в кадр
```

Между `shade` и следующим `extend` выжившие уплотняются в новый список одним
атомиком, поэтому четвёртый отскок диспатчится по путям, которые до него
дожили, а не по пикселям, закончившимся на первом.

**Что этим покупается.** Мегаядро несёт весь путь одним потоком: варп работает,
пока не закончится самый длинный путь в нём, а регистровый след — объединение
всех стадий, через которые путь мог бы пройти. Это и держит занятость внизу.
Замер, ради которого в `WavefrontStats` живёт `aliveAtBounce`, показывает, за
что идёт борьба: **100% → 59% → 17% → 10% → 6% → 1% → 1%** живых путей по
отскокам.

**Размер волны — решение, а не константа.** Одна волна — ровно один сэмпл на
каждый пиксель. Тогда индекс пути равен индексу пикселя, и накопление в конце
это обычное сложение: без атомиков и без коллизий, два пути одной волны не
могут захотеть один пиксель. Плата — буферы размером с кадр: 1280×720 это
**288 МиБ**, 320×180 — 18 МиБ.

```cpp
class WavefrontTracer {
    bool build(std::string* error = nullptr);

    bool uploadStatic(const Scene&, std::string* error = nullptr);   // мир, палитра, свет, текстуры
    bool uploadDynamic(const Scene&, std::string* error = nullptr);  // каст, спрайты, пропы
    bool upload(const Scene&, std::string* error = nullptr);         // и то и другое

    bool render(const Scene&, const PathSettings&, Image& out,
                RenderTargets* aovs = nullptr, WavefrontStats* stats = nullptr,
                std::string* error = nullptr);

    bool countAlive = false;   // читать число выживших после каждого отскока
};
```

**Загрузка разделена не для красоты.** Мир, палитра, список источников и
текстуры блоков не меняются, пока камера ходит по одной площадке, а упаковка
дорожной площадки — это сто тринадцать тысяч блоков. Каст, спрайты и пропы,
наоборот, шот пересобирает каждый кадр: новая поза — новый набор коробок.
Сравнить указатель на сцену достаточно, чтобы понять, что площадка та же.

`countAlive` стоит синхронизации на каждом отскоке, поэтому по умолчанию
выключен: это измерительный прибор, а не отчёт.

## block_textures_gpu.hpp

Вьюпорт уже строит массив текстур с той же раскладкой — слой `id * 6 + face`,
тинт и наложение травы запечены. Отдать его же трассировщику было бы опрятно, и
**нельзя**, по трём причинам, каждая из которых важна:

- Вьюпорт подставляет воде и стеклу **превью-цвет** — оттенок, который среда
  дала бы через несколько блоков пути. Растеризатор среду проследить не может,
  трассировщик может, и это значение ему не нужно никогда.
- Вьюпорт хранит восьмибитный sRGB. CPU-трассировщик читает float-текстуру и
  умножает тинт в линейном свете — восемь бит после тинта сверка была бы
  вынуждена прощать.
- Вьюпорт строит мипы. У компьют-шейдера нет производных, значит LOD не
  определён, а CPU и так читает полное разрешение.

Поэтому здесь свой массив: RGBA32F, линейный, без мипов. Общее у них одно, и
оно же главное — каждый тексель приходит из того самого
`BlockTextureLibrary::sampleAlbedo`, который зовёт CPU. Два массива не могут
значить разное, потому что ни один из них ничего не решает.

Библиотека может быть `nullptr`, и это не особый случай: каждый слой тогда
запекает плоский цвет палитры с тинтом верхней грани — ровно то, на что
откатывается CPU. У шейдера одна ветка: он всегда сэмплирует.

## entities_gpu.hpp

Сущность к моменту трассировки уже уплощена: `EntitySet::add` разрешает позу
через скелет и превращает модель в список ориентированных коробок в мировом
пространстве, каждая со своими шестью прямоугольниками скина. **Здесь это не
повторяется** — `EntitySet::boxes()` отдаёт те же коробки, по которым ходит CPU,
и остаётся только переписать их в раскладку, читаемую шейдером (272 байта на
коробку, персонаж — двадцать четыре).

Собрать коробки заново из `entities()` значило бы завести вторую реализацию той
же цепочки суставов. Они совпадали бы ровно до того дня, когда перестали, а
симптомом была бы рука, стоящая чуть иначе в двух рендерах одного кадра.

Скины ложатся в массив текстур по слою на скин, RGBA32F и линейно — по той же
причине, что и блоки. Выборка — `texelFetch`: CPU адресует тексели напрямую и
никогда не фильтрует, а скин это пиксель-арт, который билинейка размажет.

Прямоугольники граней едут в `GpuBox::faces` теми же, какими их заполнил
`buildPlayerModel`. Раскладка скина живёт в одном месте — `Skin::faceRect`, —
поэтому её починка чинит сразу CPU, вьюпорт и GPU; см.
[соглашения](conventions.md#раскладка-скина).

## offgrid_gpu.hpp

Спрайты и пропы упакованы вместе, потому что им нужно одно и то же, а больше
никому: **дерево**. Миру BVH не нужен — сетка чанков им уже является; коробкам
сущностей не нужен — шестьдесят штук просканируются быстрее, чем дерево
обойдётся. Эти двое висят в открытом воздухе, и их тысячи.

Как и с коробками, ничего не уплощается дважды: `SpriteSet::flats()`,
`PropSet::flats()` и `Bvh::nodes()` отдают то, по чему ходит CPU. Дерево здесь
тоже **не перестраивается**: вторая сборка могла бы выбрать другое разбиение, и
тогда два рендерера расходились бы в том, какие примитивы принадлежат узлу, — а
это не та разница, которую показывает картинка.

Одна вольность всё же взята. Листья `Bvh` хранят индексы в массив `order`,
поэтому примитивы загружаются **переставленными** по нему: тогда диапазон листа
адресует буфер напрямую и массив порядка ехать не обязан. Это не сокращение
пути, а на один storage-блок меньше из шестнадцати, разрешённых стадии, — а на
этом этапе занят каждый.

## denoise_gpu.hpp

```cpp
class Denoiser {
    bool build(std::string* error = nullptr);
    bool run(const RenderTargets&, const DenoiseSettings&, Image& out,
             std::string* error = nullptr);

    double lastUploadSeconds() const;
    double lastFilterSeconds() const;
    double lastReadbackSeconds() const;
};
```

Очередь ему выпала по арифметике, а не по амбиции. Когда трассировщик переехал,
кадр 1280×720 этого фильма стал стоить около трёх с половиной секунд
трассировки и почти девять секунд фильтрации: фильтр не стал медленнее ни на
йоту, он просто превратился из десятой части кадра в его большую половину.

**Почему он стоит отдельно, а не стадией волны.** Он мог бы читать буферы,
которые к концу `resolve` и так лежат в видеопамяти. Но фильтр, принимающий
`RenderTargets`, — это замена CPU-фильтру один в один: тот же вызов на том же
месте, пригодный обоим трассировщикам и всему, что соберёт эти буферы иначе.

Довод про шину, определивший форму трассировщика, сюда **не переносится**. Та
конструкция платила PCIe на каждом отскоке; эта платит один раз за четыре
буфера размером с кадр и один раз за ответ — миллисекунды против секунд
фильтрации. Правило проверяется замером, а не наследуется.

Контракт тот же, что у CPU-версии: без вспомогательных буферов вход
возвращается неизменным, а не размывается вслепую.

## Как это встраивается в дубль

`anim/` про OpenGL не знает и знать не будет. У `Take` для этого два
необязательных шва, оба по умолчанию ведут на CPU:

```cpp
std::function<bool(const Scene&, const PathSettings&, RenderTargets&)> renderer;
std::function<Image(const RenderTargets&, const DenoiseSettings&)> filter;
```

`renderer` обязан заполнить `targets` ровно так, как это делает `renderPath`;
`filter` подменяет шумоподавитель и спрашивается только при `denoiseFrames`.
Дубль остаётся циклом по кадрам. Живой пример — `scenes/film.cpp`: в `renderer`
сидит `WavefrontTracer`, перезагружающий площадку только при смене сцены, в
`filter` — `gpu::Denoiser`.

## Измерено

RTX 4050 Laptop, i7-13620H, 1 сентября 2026, `scene_test_gpu` и
`scene_film time=raise gpu`.

**Обход, партия лучей с CPU** (250 тыс. лучей, дорожная площадка):

| | CPU | GPU целиком | Только диспатч |
|---|---|---|---|
| камерные лучи | 0.063 с | 0.013 с (4.7×) | 43× |
| теневые лучи | 0.061 с | 0.013 с (4.8×) | 28× |

Разрыв между двумя правыми колонками и есть цена шины — то самое измерение,
из-за которого через неё больше не ходит ничего, кроме готового кадра.

**Интегратор, 320×180, 512 спп, 6 отскоков, плоская палитра:**

| | Время | Против CPU |
|---|---|---|
| CPU, 16 потоков | 17.53 с | — |
| мегаядро | 1.07 с | 16.5× |
| волна | 3.14 с | 5.6× |

На кадре такого размера волна мегаядру **проигрывает**, и это честный результат:
диспатчей 26 тысяч, и накладные расходы съедают выигрыш от уплотнения. Волна
берёт другим — она единственная умеет текстуры, сущности, спрайты и пропы, а на
киношном разрешении её накладные расходы амортизируются.

**Волна на сценах, которых мегаядро не умеет** (320×180, 512 спп):

| Сцена | CPU | Волна | Отличие от CPU (относительный L1) |
|---|---|---|---|
| с текстурами блоков | 19.76 с | 2.80 с | 0.0087 |
| три персонажа, 36 коробок | 41.29 с | 3.60 с | 0.0154 |
| всё сразу: 403 спрайта, 2 пропа | 45.69 с | 4.62 с | 0.0173 |

**Кадр фильма, 1280×720, 64 спп, 6 отскоков** (шот `raise` — с пылью, самый
дорогой): GPU трассирует **3.42 с** при 3264 диспатчах и 288 МиБ на карте. CPU
в том же прогоне, парой минут раньше — 68.16 с (19.9×), 173.2 млн лучей.
Шумоподавитель — **0.08 с** против 8.87 с. Кадр целиком на CPU — 77.7 с.

> Отношение CPU/GPU без указания теплового состояния машины бессмысленно: тот
> же кадр на холодном и на прогретом процессоре отличается втрое. Цифры выше
> сняты **в одном прогоне** с разницей в минуты, поэтому их можно ставить
> рядом. В остальных случаях цитируй абсолютные секунды GPU, а не ускорение.

## Что проверяется и как

`scenes/test_gpu.cpp`, и построен он как проверка DDA в `test_prop`: у эталона
спрашивают только то, на что он способен ответить.

**Точно:** попадание или промах, координата блока, id блока, ось грани и знак
нормали. Это дискретные решения, и расхождение в них означает, что кто-то ходит
по сетке неправильно.

**С допуском:** `t` и следующие из него uv грани. GLSL вправе свернуть
умножение со сложением в FMA там, где MSVC не свернул, и делению разрешён
другой последний бит. Требовать побитового равенства `t` — требовать того, чего
два языка друг другу не обещали.

Картинки сверяются по относительному L1 и отдельно по AOV: средний косинус
между нормалями 0.9997, относительная ошибка глубины 8.2e-04. Шумоподавитель на
синтетике совпадает с CPU **побитово** (относительный L1 ровно 0.000000) — он
детерминирован, в отличие от интегратора.

Отдельная тонкость, которую тест печатает, а не прячет: 27 тысяч лучей из 250
тысяч в сцене «внутри воды» дают ячейку, отличающуюся на единицу — все они идут
точно по плоскости между двумя ячейками, где `floor()` от почти-целого решает в
разные стороны. Это не другой обход, и тест говорит именно это.

---

## Чего на GPU нет

- **Мегаядро не знает ничего, кроме вокселей.** Текстуры, сущности, спрайты и
  пропы есть только у волны.
- **Стили материалов и пост** остаются на CPU — кроме шумоподавителя. Cel,
  bloom, грейдинг, виньетка и зерно считаются по готовому кадру и стоят доли
  секунды.
- **Память волны растёт с кадром**, а не с числом отскоков: 288 МиБ на
  1280×720. Кадр 4K потребует другого размера волны — а вместе с ним атомиков
  при накоплении.
- **Шестнадцать storage-блоков на стадию** — предел, в который волна уже
  упёрлась; поэтому примитивы BVH едут переставленными.
- **Побитового совпадения с CPU нет и не будет.** См. выше: это свойство
  арифметики, а не недоделка.
