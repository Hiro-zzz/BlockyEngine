# API: engine/anim

[← README](../README.md) · [core](api-core.md) · [world](api-world.md) · [scene и render](api-render.md) · [gpu](api-gpu.md) · [assets и entity](api-assets.md) · [sprite](api-sprite.md) · [prop](api-prop.md) · [rig](api-rig.md) · [anim](api-anim.md) · [physics](api-physics.md) · [script](api-script.md) · [video](api-video.md)

Время входит в движок здесь и больше нигде. Рендерер по-прежнему принимает
`const Scene&` и возвращает картинку. Анимация — это цикл, который
пересобирает дешёвую половину сцены и зовёт его снова.

Риг об этом не знает, и это не недоделка. Скелет позирует; секунды кормят его
готовой `Pose`. Путать одно с другим — как путать арматуру с таймлайном в том
самом редакторе, ради побега от которого всё писалось.

## Сцена и дубль

Типа `Stage` нет и не будет. Дорогое — мир, текстуры, список источников —
строится **один раз**, обычным кодом, до начала дубля. Дешёвое — всё, до чего
дотягивается `shot`. Разница стоит ровно нуля новой лексики:

```cpp
Scene scene(palette::registry());
scene.world = generateIsland();          // один раз
scene.blockTextures = &textures;         // один раз

Take take;
take.scene = &scene;
take.shot = [&](Scene& s, const Frame& f) {
    s.camera.lookAt(orbit(f.time), centre);   // каждый кадр
    entities.clear();
    figure.pose = walk.at(f.time);
    entities.add(figure);                     // add() сразу уплощает позу
    s.entities = &entities;
};
```

`EntitySet::add` запекает позу в мировые коробки на месте — поэтому трассировщику
дёшево, и поэтому новая поза требует нового набора. Переиспользовать вчерашний
набор с сегодняшней позой — получить персонажа, который вежливо стоит в первом
кадре до конца дубля и ни на что не жалуется.

## timing.hpp

Единственное место, которое знает, что такое кадр.

```cpp
struct Frame {
    int   index = 0;     // 0 .. count-1, считая каждый кадр на диске
    float time  = 0.0f;  // секунды, уже квантованные stepEvery
    float t01   = 0.0f;  // time / duration, в [0, 1]
    float dt    = 0.0f;  // шаг между *просчитанными* кадрами, не между любыми
    bool  held  = false; // этот кадр — копия предыдущего; shot это не смотрит
};

struct Timing {
    float duration = 4.0f;  // секунды готовой анимации
    int   fps = 24;
    int   stepEvery = 2;    // 1 — каждый кадр новый, 2 — на двойках

    int   frameCount() const;
    int   renderedFrameCount() const;   // сколько реально уйдёт в трассировщик
    Frame frameAt(int index) const;
};
```

### На двойках

`stepEvery = 2` держит каждую позу два кадра. Это классические двенадцать в
секунду ограниченной анимации — и на блочной фигуре это стиль, а не экономия,
которая стесняется назваться. Это ещё ровно половина рендера: второй кадр
пары **байтовая копия** первого, а не второй проход трассировщика.

Тождество не вычисляется и не «угадывается по похожести». Время, которое
видит `shot`, квантуется **до** вызова, поэтому оба кадра пары получают одно
и то же число и обязаны дать одну и ту же сцену.

Отсюда единственное правило, которое `shot` обязан соблюдать: **быть чистой
функцией `Frame`**. Часы стены, глобальный счётчик или незасеянный ГПСЧ внутри
дубля — это способ получить два «одинаковых» кадра, которые не одинаковы, в то
время как движок честно копирует первый. Всё, что меняется, меняется от
`Frame`. Всё, что не меняется, живёт снаружи цикла.

`index / fps` нарочно не предлагается. Это был бы самый короткий способ
случайно обойти hold и не понять, почему анимация на двойках вдруг стоит как
на единицах.

## ease.hpp

Кривые под боксы, а не под выезжающую панель настроек. Обычная библиотека
easing — коллекция способов быть гладким. Блочному персонажу нужно другое:
**постоять, потом шагнуть**. Гладкость здесь опция, не умолчание.

```cpp
namespace ease {
using Curve = std::function<float(float)>;

float linear(float t);
float smooth(float t);    // smoothstep — для камеры, которой не следует кичиться
float in(float t);
float out(float t);
float step(float t);      // прыжок на дальнем конце; слайдшоу поз, на двойках — стоп-моушен

Curve hold(float fraction = 0.6f);         // стоять fraction сегмента, остаток — движение
Curve back(float overshoot = 1.70158f);    // промахнуться и сесть
Curve anticipate(float amount = 0.18f);    // сначала отшатнуться
Curve snap(float wind = 0.14f, float overshoot = 1.3f);  // все три сразу
Curve bounce(int bounces = 3, float decay = 0.42f);
}
```

Каждая кривая отображает `[0, 1]` примерно в `[0, 1]`. «Примерно» — потому что
`back` и `anticipate` диапазон **намеренно** покидают: перелёт и есть весь
смысл, и `Track` с удовольствием экстраполирует значение за ключ.

`hold` — рабочая лошадь. Поза, которая стоит и потом едет, читается как
решение. Та же дуга, размазанная равномерно, читается как дрейф.

Два разных «рваных» — это два разных ручки, и мешать их не стоит:

| Ручка | Что квантует |
|---|---|
| `Timing::stepEvery` | **когда** сцена сэмплируется. На двойках весь кадр стоит два кадра — и это то, что делит рендер пополам |
| кривая на ключе | **как** значение проходит свой сегмент. `ease::hold` стоит, потом бросает |

По отдельности обе помогают. Вместе это стоп-моушен.

## track.hpp

Трек — удобство **над** швом, а не сам шов. Дубль есть функция времени, поэтому
`sin(f.time * 3.0f)` — уже вполне законная анимация и не нуждается ни в чём
отсюда. Трек добавляет другой способ думать: вот эта поза здесь, вон та там.
Оба свободно мешаются внутри одного `shot` — `scene_turntable` так и сделан:
камера считается тригонометрией, поза живёт на трёх ключах.

```cpp
template <class T>
class Track {
    Track& key(float time, const T& value);
    Track& key(float time, const T& value, ease::Curve curve);
    Track& stepped();                 // все позднейшие ключи — step
    Track& curve(ease::Curve);        // кривая по умолчанию для следующих key
    T      at(float time) const;

    bool   empty() const;
    size_t size() const;
    float  startTime() const;
    float  endTime() const;
};
```

Кривая, заданная с ключом, управляет сегментом, который **начинается** в нём.
Кривая последнего ключа никогда не используется.

Снаружи ключей трек держит крайние значения, а не экстраполирует: выбежать за
конец дубля должно значить «замереть», а не «улететь».

Два ключа в один миг — это склейка, а не деление на ноль.

Трек из одного ключа держит одно значение вечно — аккуратный способ оставить
что-то анимируемым, не анимируя пока.

`at` зовёт `animLerp`. Чтобы ключить свой тип, достаточно перегрузки — см. ниже.

## blend.hpp

Смешивание живёт в `anim/`, а не в `rig/`, нарочно. Скелет знает про родителей
и оси, не про секунды. Движется **поза**.

```cpp
T         animLerp(const T& a, const T& b, float t);   // float, Vec3, и дальше
JointPose animLerp(const JointPose& a, const JointPose& b, float t);
Pose      animLerp(const Pose& a, const Pose& b, float t);
Camera    animLerp(const Camera& a, const Camera& b, float t);

Pose poseAdd(const Pose& base, const Pose& overlay, float weight = 1.0f);
```

Интерполяция углов Эйлера здесь не компромисс. Суставы, которые растит риг, —
шарниры: локоть, колено, челюсть крутятся вокруг одной оси, и смешать один
угол вокруг одной оси — это правильный ответ, а не приближение к нему.
Кватернион понадобится в день, когда голова пойдёт за целью, пока под ней
крутится торс. Пока такого кадра нет, его и нет.

Сустав, о котором одна из поз молчит, читается как покой. Поэтому поза с
челюстью мешается с позой без неё — просто без челюсти.

`poseAdd` кладёт одну позу поверх другой: повороты и сдвиги складываются,
шкала перемножается (`1` в оверлее ничего не делает). Дыхание поверх ключей,
не зная про ключи.

У камеры не смешивается только режим проекции — это перечисление, и промежутка
у него нет. Склейка ортографии с перспективой есть склейка, а не проезд;
результат берёт режим `a`.

## take.hpp

Цикл, который превращает дубль в последовательность на диске и в файл, который
можно открыть.

```cpp
struct Take {
    std::string name = "take";
    Timing      timing;
    PathSettings settings;
    Scene*      scene = nullptr;                          // не владеет
    std::function<void(Scene&, const Frame&)> shot;       // шов
    std::function<Image(RenderTargets&, const Frame&)> finish;  // после denoise

    DenoiseSettings denoiseSettings;
    bool            denoiseFrames = true;
    ToneParams      tone;

    std::string outputDir;     // пусто → out/<name>
    std::string apngPath;      // пусто → out/<name>.png
    bool writeApng = true;
    int  apngPlays = 0;        // 0 — крутить вечно

    std::string mp4Path;       // пусто → out/<name>.mp4
    bool writeMp4 = false;     // по запросу, не сюрпризом
    int  videoQp = 24;

    bool resume = true;
    int  firstFrame = 0;
    int  lastFrame = -1;       // -1 — до конца
    bool progress = true;
};

bool renderTake(const Take&, TakeStats* = nullptr, std::string* error = nullptr);
bool assembleApng(const Take&, std::string* error = nullptr);
bool assembleMp4(const Take&, std::string* error = nullptr);
std::string takeFramePath(const Take&, int index);
```

`finish` — место cel-шейдинга, грейдинга, виньетки. Без него на диск идёт
шумоподавленный цветовой буфер как есть.

Зерно трассировщика **намеренно одно на весь дубль**. Фиксированный сид держит
остаточный шум на месте, и он сидит, а не кипит. Менять сид с кадром — выбор,
который кажется правильным первым, и он как раз не тот. Внутри hold вопроса
нет: кадр копируется.

### Где считается кадр

Дубль по умолчанию зовёт `renderPath` и `denoise`. Два необязательных шва
позволяют подменить обоих, не рассказывая `anim/` про существование OpenGL:

```cpp
std::function<bool(const Scene&, const PathSettings&, RenderTargets&)> renderer;
std::function<Image(const RenderTargets&, const DenoiseSettings&)> filter;
```

`renderer` обязан заполнить `targets` ровно так, как это делает `renderPath` —
цвет и три вспомогательных буфера; `filter` спрашивается только при
`denoiseFrames`. Это `std::function`, а не флаг, именно поэтому: слой времени
остаётся циклом по кадрам и не заводит ветку «а если видеокарта». Кто хочет
карту — передаёт `gpu::WavefrontTracer` и `gpu::Denoiser` снаружи, см.
[api-gpu.md](api-gpu.md).

### На диске

Каждый кадр пишется в `out/<name>/0000.png`, включая удержанные — они байтовые
копии, а не второй рендер. Это стоит немного места и покупает многое:

- дубль возобновляется: кадр, который уже на диске, не считается снова;
- один плохой кадр пересчитывается удалением одного файла;
- два процесса могут разрезать диапазон и работать сразу;
- каталог — обычная последовательность картинок, её читает что угодно.

Рядом лежит `take.txt` — подпись настроек (`ширина, spp, fps, step, duration`).
Resume умеет спросить только «файл на месте?», а файл не умеет сказать, чем
его считали. Без подписи поднять разрешение и запустить снова значило бы
пропустить 96 вчерашних кадров и отрапортовать успех. Несовпавшая подпись —
отказ, а не полузаполненный каталог из двух разных картинок.

APNG собирается из этих файлов **без декодирования и без повторного сжатия**:
сжатые данные кадров поднимаются как есть, прогоны одинаковых кадров схлопываются
в один кадр с длинной задержкой. На двойках это половина рендера **и** половина
файла — приятная вещь, которую формат способен вознаградить.

MP4 по умолчанию выключен. APNG — тот же PNG, который уже открывает любой
просмотрщик, без потерь. Завернуть исходники в контейнер с квантованием —
решение, которое дубль не принимает за автора. `scene_sway` включает его явно.

И APNG, и MP4 собираются с диска, поэтому оба можно дособрать после оборванного
прогона: `assembleApng` / `assembleMp4`. Частичный диапазон (`firstFrame` /
`lastFrame`) кадры считает и **не** собирает контейнер — это сознательно
недоделанное состояние, а не ошибка.

Подробности контейнеров — [api-video.md](api-video.md), APNG как кодек —
[api-core.md](api-core.md#pnghpp).

## Что это добавляет в кадр

Ничего, чего не умел один `renderPath`. Дубль — это N раз тот же кадр, в котором
поза и камера — функции времени. Персонаж отбрасывает ту же тень, попадает в то
же отражение и участвует в том же GI, потому что для трассировщика это по-прежнему
просто сцена.

## Чего нет

- **Размытия движения.** Каждый кадр дубля — обычный still. На двойках блок и
  так стоит достаточно долго, чтобы глаз успел его прочитать, и это не отговорка,
  а эстетика.
- **Эмиттеров и симуляции.** Частица в статичном кадре была застывшим мгновением;
  в дубле она по-прежнему ставится в `shot`, если автор так напишет. Движка частиц
  нет — есть функция времени, которая может вызывать `scatter::`.
- **IK.** По-прежнему ставишь углы. Анимация этого не отменяет и не чинит.
- **Перестройки мира каждый кадр.** Можно, технически: `shot` видит всю сцену.
  Дорогое, что строилось один раз, тогда перестаёт быть построенным один раз, и
  дубль на двойках внезапно стоит как дубль на единицах, только с генерацией
  сверху.
