# API: engine/rig и engine/entity/rigging

[← README](../README.ru.md) · [core](api-core.md) · [world](api-world.md) · [scene и render](api-render.md) · [gpu](api-gpu.md) · [assets и entity](api-assets.md) · [sprite](api-sprite.md) · [prop](api-prop.md) · [rig](api-rig.md) · [anim](api-anim.md) · [physics](api-physics.md) · [script](api-script.md) · [video](api-video.md)

Скелет с суставами и инструменты, которые режут модель на более мелкие части.

**Риггинг — это не анимация.** Предложение пережило появление секунд и стало
от этого только точнее. Риг — структура, **через которую позируют**. Секунды
живут в [`anim/`](api-anim.md) и кормят его готовой `Pose`. Путать их — как
путать арматуру с таймлайном в том самом редакторе, ради побега от которого
всё писалось.

---

## Что умеет скелет и не умела плоская поза

| | Плоская `Pose` (было) | Скелет (стало) |
|---|---|---|
| Родительство | Нет. Каждая часть крутится вокруг своей оси в одиночку | Есть. Поворот торса уносит голову и руки |
| Число суставов | Ровно шесть, по одному на `SkinPart` | Сколько попросишь: локти, колени, челюсть, бровь |
| Кому служит | Только сущностям | Сущностям **и** пропам — скелет не знает, что держит |

Раньше повёрнутый торс оставлял собственные руки висеть в воздухе рядом.

## rig.hpp

```cpp
struct Joint     { std::string name; int parent; Vec3 pivot; };
struct JointPose { Vec3 rotationDegrees; Vec3 offset; float scale; };

class Skeleton {
    int  add(const std::string& name, int parent, Vec3 pivot);   // -1 при плохом родителе
    int  find(const std::string& name) const;                    // -1, если нет
    bool descendsFrom(int index, int ancestor) const;

    void resolve(const Pose&, std::vector<Mat4>& out) const;
    void resolveRest(std::vector<Mat4>& out) const;
};
```

**Родитель обязан уже существовать.** Одно это правило делает хранение
топологическим, а `resolve` — одним проходом вперёд без рекурсии и без проверки
на циклы.

Локальное преобразование сустава:

```
translate(pivot + offset) · Rz · Ry · Rx · translate(−pivot)
```

Порядок `Z, Y, X` тот же, что был у плоской позы, поэтому знаки в
[соглашениях](conventions.md#ориентация-сущностей) остались в силе.

### Pose

```cpp
JointPose& operator[](int joint);                // растёт под индекс
const JointPose& operator[](int joint) const;    // вне диапазона — покой
JointPose& at(const Skeleton&, const std::string& name);

static Pose standing(), striding(float), waving(float = 150), tPose();
```

Поза намеренно **не привязана к скелету**: сустав, о котором ей нечего сказать,
остаётся в покое. Поэтому поза, написанная для рига с челюстью, применима и к
ригу без неё — просто без челюсти. И поэтому `Pose::striding()` существует
обычным значением.

Именованный доступ на неизвестное имя возвращает черновую запись, а не падает.

### Стандартные суставы

Индексы зафиксированы в этом порядке — тот же приём, что у палитры блоков:

```
0 Root      1 Body      2 Head      3 RightArm
4 LeftArm   5 RightLeg  6 LeftLeg   (HumanoidCount = 7)
```

Иерархия, которую строит `buildPlayerModel`:

```
root
├── body            ось на поясе (0,12,0)
│   ├── head        (0,24,0)
│   ├── rightArm    (5,22,0)
│   └── leftArm     (−5,22,0)
├── rightLeg        (2,12,0)
└── leftLeg         (−2,12,0)
```

Торс крутится вокруг **пояса, а не шеи**, поэтому сгибание уносит весь верх, а
ноги остаются стоять.

> ### Знак зависит от того, с какой стороны от оси часть
>
> Это самое лёгкое, что можно перепутать во всём риге.
>
> Конечность **висит ниже** своей оси, поэтому положительный поворот вокруг X
> уводит её вперёд, к −Z. Торс **поднимается выше** пояса, поэтому тот же
> положительный поворот кладёт его **назад**. То же с челюстью: она ниже своего
> шарнира, значит открывается отрицательным углом.
>
> Ошибка в знаке не ломает ничего заметно — фигура просто гнётся не туда.
> Оба случая закреплены в `test_rig`.

## entity/rigging.hpp

### Разрез части

```cpp
enum class Chain { FromLow, FromHigh, Siblings };

std::vector<int> split(EntityModel&, int joint, int axis, int segments,
                       Chain chain, const std::string& prefix);
```

Режет все коробки сустава на `segments` кусков вдоль оси, каждому даёт свой
сустав. Возвращает суставы по порядку вдоль оси, нулевой — нижний конец.

`FromHigh` — то, что нужно конечности: рука висит с плеча сверху, значит
корень цепи это верхний сегмент, а предплечье шарнирится от него.

**Прямоугольники скина режутся вместе с коробкой.** Это кропотливая часть:
коробка знает шесть прямоугольников, и разрезать её пополам значит разрезать их
тоже — вдоль верной текстурной оси, в верную сторону, для каждой грани.
Ошибка не падает и не выглядит сломанной: она выглядит как «скин слегка не
такой», и это не видно, пока кто-нибудь не уставится на кадр, не понимая, что
не так. `faceAxes()` в `model.hpp` — обратная к `boxFaceUv()`, и именно она
держит их в согласии.

> Две грани, смотрящие вдоль оси разреза, — особый случай: **каждый** сегмент
> сохраняет исходный прямоугольник целиком, чтобы внутренний срез читался
> заглушкой, а не дырой. Пометить их недействительными было бы правдивее для
> сплошной конечности и куда хуже на вид: недействительная грань пропускает
> луч насквозь.

Прямоугольник, не делящийся нацело, режется настолько ровно, насколько
позволяют целые числа: куски могут отличаться на пиксель.

### Готовые случаи

```cpp
int addHinge(EntityModel&, int joint, const std::string& name);   // локоть, колено
int addJaw(EntityModel&, int headJoint, float jawPixels = 3.0f,
           const std::string& name = "jaw");
```

`addHinge` режет конечность пополам поперёк и возвращает сустав дальней
половины — тот, который поворачивают, чтобы согнуть.

`addJaw` отрезает нижние `jawPixels` головы, возвращает остальное на сустав
головы и вешает шарнир **в затылке**, где челюсть и поворачивается, а не
посередине черепа, куда его поставил бы обычный разрез.

### Привязки

```cpp
struct Attachment { name, parent, pivot, origin, size, inflate, cutout,
                    part, layer, faces[6] };
int attach(EntityModel&, const Attachment&);

Attachment attachmentFrom(name, parent, origin, size, const SkinRect&);
SkinRect   subRect(const SkinRect&, int x, int y, int w, int h);
```

Новая коробка на новом суставе. Так делаются мелочи: бровь, ухо, серьга.
`subRect` вырезает несколько текселей грани, на которой деталь сидит.

### Вторые слои

```cpp
int detachLayer(EntityModel&, SkinPart, SkinLayer, const std::string& name);
```

Переносит все коробки слоя на новый сустав, дочерний к тому, где они были.
Новый сустав наследует ось родителя, поэтому **само отделение ничего не
двигает** — меняется только то, чем слой управляется. После него шляпа
наклоняется, не утаскивая голову, а куртка висит, пока торс поворачивается.

```cpp
bool reparent(EntityModel&, int joint, int newParent);
```

Отказывается от цикла и от родителя с бо́льшим индексом: порядок
«родители раньше» — это то, что держит `resolve` одним проходом.

> **Шляпа — та же коробка, что голова, раздутая на полпикселя.** Любой
> заметный наклон уводит её козырёк на глаза. Это честно и бесполезно для
> кадра, где нужно лицо: в `scene_rigging` кепка развёрнута вокруг вертикали,
> а не наклонена.

## prop/prop_rig.hpp

Тот же скелет уровнем крупнее: сущность привязывает к суставам коробки, риг
пропа — целые модели. Это естественное зерно для вещи, собранной из отдельных
кусков: сундук с крышкой, фонарь на кронштейне, кран со стрелой.

```cpp
struct PropRigPart { const VoxelModel* model; int joint; Vec3 offset; Vec3 tint, emissionScale; };

struct PropRig {
    Skeleton skeleton;
    std::vector<PropRigPart> parts;
    int  addPart(name, parent, pivot, const VoxelModel*, Vec3 offset = {});
    void attach(int joint, const VoxelModel*, Vec3 offset = {});
};

void addRigged(PropSet&, const PropRig&, const Pose&, const PropPlacement&);
bool rigBounds(const PropRig&, const Pose&, Vec3& lo, Vec3& hi);
```

| `PropPlacement` | По умолчанию | Смысл |
|---|---|---|
| `position` | — | Куда встаёт риг |
| `yaw/pitch/roll` | `0` | Разворот целиком |
| `voxelSize` | `1/16` | Мировых единиц на воксель |
| `centreOnBounds` | `false` | Считать `position` серединой габаритов покоя |
| `tint` / `emissionScale` | `1` | Умножаются на те, что у части |

К моменту, когда трассировщик это видит, части неотличимы от обычных пропов:
`addRigged` кладёт каждую в тот же `PropSet` через `addTransformed`.

Масштаб живёт в размещении и **равномерен**, поэтому составленная матрица
остаётся жёсткой плюс равномерный масштаб — и параметр луча её переживает.

## Как это проверяется

Главный тест — **«разрез ничего не меняет»**. Базовый слой после разреза
сверяется побайтово: несколько тысяч лучей до и после, тот же скин-паттерн, где
каждый тексель кодирует свои координаты, — любое смещение UV меняет цвет.
Семь случаев разреза, все проходят точно.

С внешними оболочками утверждение слабее и тоже точное: **силуэт** не меняется —
та же поверхность на том же расстоянии везде. Цвет там не утверждается, и
намеренно: оболочка каждого сегмента раздута со всех шести сторон, поэтому на
разрезе две оболочки перекрываются полоской в полпикселя и внутри неё расходятся
на один ряд текселей. Это следствие того, что `inflate` — один скаляр на
коробку; альтернатива — раздутие по граням ради разницы, которую никто не
увидит.

---

## Чего нет

- **Обратной кинематики.** Ставишь углы, а не «положи ладонь сюда». Для
  статичного кадра это редко мешает, и IK ложится сверху, ничего не трогая.
- **Скиннинга с весами.** Коробка принадлежит **одному** суставу целиком.
  Для блочных моделей это не приближение, а точное описание.
- **Ограничений на суставы.** Локоть согнётся назад, если попросить.
- **Рига во вьюпорте нет отдельно** — вьюпорт использует тот же `resolve`, что
  и трассировщик, так что позы он показывает; спрайты и пропы по-прежнему нет.
- **Разреза пропов.** `split` работает по коробкам сущности; воксельную сетку
  режут, строя две модели.
- **Секунд.** Ничто здесь не движется во времени и не должно. Цикл по кадрам —
  в [api-anim.md](api-anim.md), и он кормит риг готовыми позами.

## entity/face.hpp — риг глаз

Глаза персонажа **нарисованы**, а не смоделированы: два-три текселя на плоской
передней грани головы. Поэтому риг для них — три шага, и `rigging.hpp` в
одиночку ни один из них не делает.

```cpp
EntityModel model = buildPlayerModel(skin);
face::EyeRig rig = face::buildEyeRig(model, skin);   // skin МЕНЯЕТСЯ

Pose pose;
face::gaze(rig, pose, -0.7f, 0.0f);   // взгляд влево для сущности; значения в [-1, 1]
```

Четыре сустава: белки на голове, зрачки на своих белках. Сдвинуть белок —
это увезти глаз по щеке, то есть изуродовать лицо, а не скосить взгляд.
Взгляд — тёмное, которое едет **внутри** белого. Глаз одной коробкой, на
которой нарисовано и то и другое, этого сделать не может вообще.

`gaze` пишет в зрачки и зажимает ход: зрачок за краем белка — это не более
упорный взгляд, а дыра в лице.

### Почему скин меняется

`rigging::attach` умеет только **добавлять**. Оставь нарисованные глаза на
месте — и персонаж, скосивший взгляд, получит нарисованные плюс новые, причём
молча. Карьера оптика, не портрет.
Поэтому `buildEyeRig` закрашивает найденные глаза цветом их окружения и рисует
новую пару в области изображения, которую не читает ни одна часть модели.

Свободное место **вычисляется**, а не предполагается: строится маска покрытия
по всем `faceRect`, и берётся первый незанятый прямоугольник. «У скина 64×64
есть место в левом верхнем углу» — факт, который верен ровно до тех пор, пока
не перестанет.

### Сдвиг, а не поворот

Глаз шириной в один-два пикселя. Поворот вокруг оси головы уносит его с лица
вовсе; сдвиг вдоль лица — это и есть то, как выглядит скошенный взгляд.
Поэтому `JointPose::offset`, а не `rotationDegrees`. Белок так не двигают:
его offset увозит глаз по щеке. `gaze` пишет offset **зрачка**.

Ещё глаз обязан **выступать** над гранью — но едва. `relief` по умолчанию
0.05 пикселя: этого хватает, чтобы луч не гадал, какую из двух компланарных
коробок взять первой. Первое значение, которое пробовали, было 0.6 — почти
четыре сантиметра рельефа на глазу в двенадцать, и персонаж получался с
глазами, **наклеенными** на лицо, а не сидящими в нём. Зрачок выступает ещё
на `pupilRelief` (0.03), чтобы очистить собственный белок.

### Поиск

`face::scanFace` ищет **зеркальную пару**, а не кожу.

Оценка «модальный цвет лица = тон кожи» разбилась о первый же настоящий скин:
там самый частый цвет передней грани — это **волосы**, закрывающие лоб. На
втором оттенки волос размазаны по стольким почти одинаковым значениям, что
частого цвета нет вовсе.

Вместо этого перебираются **все** прямоугольники в левой половине лица — их на
восьмипиксельном лице пара сотен — и каждый оценивается по трём независимым
признакам:

| Признак | Что ловит |
|---|---|
| Зеркальность | Глаз симметричен; требуется целиком, иначе кандидат отбрасывается |
| Контраст | В глазу есть светлое и тёмное. Один тексель контраста с собой не имеет, поэтому случайная точка волос получает ноль |
| Граница | У глаза есть край со всех сторон. Прямоугольник, взятый на столбец шире, включает тексель, снаружи от которого тот же цвет кожи |

Плюс запрет доходить до центрального столбца: между глазами всегда есть нос
или просто кожа.

> **Наращивание областей здесь не работает.** Глаз стоит на тексель ниже брови
> и на тексель выше щеки, и то и другое — тоже края. Любой рост склеивает все
> три в полосу и теряет глаз. Первая версия делала именно это и находила на
> одном из скинов одинокий тексель волос с уверенностью 1.00.

**Измерено** (`scene_test_face`): попадание тексель-в-тексель на всех девяти
vanilla-скинах 1.20.4 и на нарисованном скине с крупными глазами. На бледном
скине с низким контрастом позиция находится, а высота — нет: берётся только
верхний ряд, и глаз классифицируется как широкий вместо узкого. На этот случай
есть `FaceScanOptions::rightEyeOverride`.

`EyeShape` — `Wide`, когда ширина не меньше высоты, и `Narrow` иначе.
Сгенерированный глаз строится из **найденных** склеры и радужки, поэтому
остаётся глазом этого персонажа, а не палитры по умолчанию.
