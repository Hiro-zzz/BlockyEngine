# forge — редактор

[← README](../README.ru.md)

```
build\RelWithDebInfo\forge.exe
```

Три документа в одном окне: **воксельная модель**, **пиксельный холст** и
**россыпь спрайтов**. Все три выходят исходником на C++ — как сцены, как карты,
как палитры. Модель и холст выходят вдобавок картинкой, а модель и текстура —
ещё и ресурспаком для Minecraft.

Собирается из `plugins/forge/`, ядро редактирования живёт в `engine/edit/`.

---

## Почему плагин, и что это здесь значит

Сборка знает три формы. `scenes/<имя>.cpp` — один файл, одна картинка, выход.
`game/**` — всё вместе в `konstruct.exe`, потому что у игры части обязаны знать
друг о друге. Редактор не подходит ни под первую (у него документ, отмена и
человек с мышью), ни под вторую (у игры свой мир). Отсюда третья:
`plugins/<имя>/` становится `<имя>.exe`, линкующим `blocky`. Положил каталог —
собралось; регистрировать нечего.

**Плагин здесь — это программа на движке, а не библиотека внутрь него.** В
проекте ничего не загружается в рантайме, и чтобы это стало возможно,
понадобились бы стабильный C-ABI, реестр символов и история версий — настоящая
машинерия ради случая, который закрывается вторым исполняемым файлом.

Каталога `third_party/` больше нет. Он был пуст, git его не содержал и никто
на него не ссылался, а имя означает во всём мире чужой вендоренный код — то
есть ровно противоположное тому, что написано на первой странице.

## Запуск

| | |
|---|---|
| `forge` | Пустая сетка 16³ |
| `forge size=24` | Другой размер, от 1 до 128 |
| `forge name=mug` | Как будут называться выгруженные файлы |
| `forge canvas` | Начать с текстуры 16×16 |
| `forge sprites` | Начать с расстановки спрайтов |
| `forge skin` | Начать со скина 64×64, с подсказками раскладки |
| `forge open=<file.png>` | Загрузить текстуру или лист слоёв |
| `forge snapshot <png>` | Один кадр в файл, не показывая окна |
| `forge mcspace=minecraft` | Пространство имён для выгрузки в Minecraft |
| `forge mcfolder=block` | `block/` вместо `item/` внутри пака |
| `forge mcformat=15` | `pack_format` в `pack.mcmeta` |
| `forge selftest` | Проверки без окна, ненулевой код при провале |

`Tab` идёт по кругу: модель → холст → спрайты. `Esc` закрывает.

`E` выгружает документ в формы этого движка, `P` — в формы Minecraft.

## Модель

| Клавиша | Действие |
|---|---|
| Левая кнопка | Поставить воксель; удерживать — вести полосу |
| `Shift` + левая | Стереть |
| Правая кнопка | Обзор вокруг модели |
| Колесо | Ближе и дальше |
| `M` | Зеркало по X |
| `T` | Обрезать по содержимому (чистит историю отмен) |
| `1`–`8`, щелчок по палитре | Цвет |
| `Ctrl+Z` / `Ctrl+Y` | Отмена и возврат |
| `E` | Выгрузить исходник и лист |
| `P` | Выгрузить ресурспаком |

**Наведение — это тот же глагол, что в игре.** `VoxelModel::trace` отвечает на
тот же вопрос, что `World::raycast` в [player.cpp](../game/player.cpp): какая
ячейка и какая грань. Отсюда попадание даёт две ячейки — задетую и пустую перед
ней, — и «поставить» с «сломать» это они и есть, этажом ниже и против сетки
вместо решётки.

**Сетка не растёт сама.** Поставить наружу крайней грани — значит зажаться, а
не расшириться: рост сдвинул бы индекс каждого вокселя, а стек отмены — это
список индексов, и шаг до роста вернул бы ячейки не на свои места. Поэтому
размер меняют явно, и это чистит историю по той же причине.

**У пустой сетки есть плита.** Луч, не попавший ни в один воксель, ловится
базовой плоскостью `y = 0`, иначе первый воксель поставить некуда. Сама плита —
проп ровно по следу модели, а не блоки мира: ячейка мира метр поперёк, модель
из шестнадцати вокселей шириной в блок стоит поперёк четырёх ячеек, и плита из
блоков вышла бы вдвое больше того, что размечает.

## Холст

| Клавиша | Действие |
|---|---|
| Левая кнопка | Рисовать; удерживать — вести |
| `Shift` + левая | Стереть в прозрачность |
| `F` + левая | Заливка |
| `M` | Зеркало по X |
| `G` | Подсказки раскладки |
| `1`–`8`, щелчок по палитре | Цвет |
| `Ctrl+Z` / `Ctrl+Y` | Отмена и возврат |
| `E` | Выгрузить исходник и PNG |
| `P` | Выгрузить текстурой в пак |

Документ — это `ImageU8` и ничего больше, потому что именно его движок читает с
обеих сторон. 16×16 — текстура блока; 16×16 предмета — проп, как только его
выдавит `item::buildModel`; 64×64 — скин.

**Слоёв нет намеренно.** Базовый и внешний слои скина — это области **одной**
картинки 64×64, а не стопка листов, и холст со своим стеком слоёв обязан был бы
сплющивать их при сохранении, то есть заводить вторую правду о файле, весь
смысл которого в том, где что лежит.

Подсказки раскладки берутся у `Skin::faceRect`, а не переписываются рядом:
вторая копия этой таблицы была бы вторым шансом перепутать левое с правым —
ровно тот баг, который [соглашения](conventions.md#раскладка-скина) записали
как настоящий.

**Заливка точная, без допуска.** Это пиксель-арт: два тексела, которые
выглядят одинаково и не одинаковы, — ошибка, которую стоит увидеть, а не
загладить.

## Спрайты

| Клавиша | Действие |
|---|---|
| Левая кнопка | Поставить спрайт там, куда смотришь |
| `Shift` + левая | Убрать тот, что под курсором |
| Правая кнопка | Обзор |
| `[` и `]` | Меньше и больше |
| `L` | Свечение |
| `1`–`8`, щелчок по палитре | Цвет |
| `Ctrl+Z` / `Ctrl+Y` | Отмена и возврат |
| `E` | Выгрузить исходник |

Спрайт — плоский квад в мире: пылинка в столбе света, искра над костром, глиф
парящей надписи. Сцены расставляют их прямо в коде, и для шести это нормально,
а для шестидесяти невыносимо.

**Разворот замораживается при постановке.** Спрайт поворачивается к камере один
раз, в момент клика, и дальше это обычная геометрия. Это не упрощение
инструмента, а позиция всего движка, записанная в `sprite.hpp`: у поверхности,
которая переориентируется на каждый луч, нет согласованного ответа для
отражения и тени. Отсюда следствие, которое стоит знать заранее: повернув камеру
после, увидишь спрайт с ребра, и это верно, а не сломано. Ставят оттуда, откуда
будут снимать.

**Отмена здесь другая, и это ответ на тот же вопрос.** У холста и модели отмена
хранит различия по ячейкам, потому что штрих задевает горсть ячеек из тысяч, а
снимок 64-куба — полмегабайта. Здесь не работает ни одна половина довода: у
списка спрайтов нет ячеек, чтобы их индексировать, а правка добавляет или
убирает объект целиком. Десятки спрайтов по сотне байт — снимок, который ничего
не стоит.

**Светящийся спрайт ничего не освещает.** `LightSet` строится из граней
воксельного мира, и квад в него не попадает: искра видна и попадает в отражения,
но сцену не освещает. Инструмент говорит это на экране, а не оставляет на
обнаружение.

**Их наконец видно во вьюпорте.** До этого частицы и парящий текст были видны
только в трассировке — расставлять то, чего не видишь, нельзя. `buildSpriteMesh`
берёт углы квада у `SpriteSet::flats()`, то есть у той же матрицы, которую
пересекает трассировщик. Текстуры пока нет: спрайт рисуется заливкой своего
тинта, чего для «где он и какого размера» достаточно, а для картинки — нет.

## Экспорт

Три документа, и у каждого свой набор выходов.

| | `E` | `P` |
|---|---|---|
| Модель | `.hpp` и лист слоёв | ресурспак: JSON-модель и палитра |
| Холст | `.hpp` и `.png` | ресурспак: текстура |
| Спрайты | `.hpp` | отказ с причиной |

Модель выходит **двумя** файлами, и это не альтернативы.

### Исходник (`<имя>.hpp`)

Вызов `voxelize::fromLayers` — той самой функции, которой уже пользуются
модели, написанные руками. Редактор становится тем, кто её набирает.

Точен: переживают все поля материала, включая шероховатость, металличность и
свечение. Цвета пишутся **линейными** float в девять значащих цифр, а sRGB-код
идёт комментарием в конце строки. Обратный порядок — `srgbToLinear(0x4a6b8c)` —
читался бы лучше и возвращался бы хуже, а цвет, который слегка едет при каждом
проходе через редактор, это баг, о котором никто не сообщит, потому что никто
не покажет, когда он начался.

Ограничение честное: `fromLayers` читает один символ на столбец, поэтому
материалов не больше семидесяти. Больше — отказ с сообщением, а не обрезка.

Имя файла превращается в имя функции через `edit::identifierFor`: `iron mug`,
`iron-mug` и `iron_mug` дают `buildIronMug`. Сам эмиттер имя **не чинит** — он
его отвергает, потому что сгенерированный файл с функцией, названной не так,
как просили, не находится чтением места вызова.

### Лист слоёв (`<имя>_ШxВxГ.png`)

Срезы сеткой в одной картинке. Ни нового кодека, ни нового парсера, открывается
чем угодно.

Цена написана прямо: **картинка несёт цвет**. Шероховатость, металличность и
свечение до неё не доезжают — светящаяся модель выходит только исходником.

Размеры едут в **имени файла**, потому что сама картинка их сказать не может:
лист 32×32 — это четыре среза 16×8 или шестнадцать 8×8. Заголовочная строка
внутри изображения сделала бы его форматом вместо картинки; имя видно глазом,
переживает любой редактор и разбирается тремя числами.

### Холст (`<имя>.hpp` и `<имя>.png`)

Тем же правилом, что и модель: исходник — то, что держит репозиторий, картинка —
то, что отдают наружу. Исходник это вызов `pixelart::fromRows` — строки символов
плюс ключ цветов, ровно как `fromLayers` этажом выше. Текстура, написанная так,
перестаёт быть файлом ассета и становится кодом, а это уже то, чем в этом
проекте являются карты, палитры и генерируемые текстуры блоков — и причина, по
которой `game/` не требует ни одного файла ассетов.

Отказ тот же: больше семидесяти цветов — не пиксель-арт, и сообщение отправляет
к PNG, который такую плотность держит.

### Спрайты (`<имя>_sprites.hpp`)

Функция, возвращающая `std::vector<Sprite>` — то, что сцены сегодня пишут
руками. Поля, равные умолчанию, не печатаются: строка, которая есть, — это
решение, а не шум. Текстура — параметр функции, а не поле: она указывает на то,
чем владеет сцена, и сгенерированный файл не вправе её называть.

Картинкой спрайты не выходят: у списка квадов нет формы изображения. Лист и PNG
существуют потому, что сетка **и есть** картинка; это — нет.

Всё пишется в `out/forge/`.

## В Minecraft

`P` пишет дерево ресурспака в `out/forge/pack/`:

```
pack.mcmeta
assets/<пространство>/models/<папка>/<имя>.json
assets/<пространство>/textures/<папка>/<имя>.png
```

Формат модели у мода и у ресурспака один и тот же, поэтому один выход служит
обоим. Пространство имён, папку и `pack_format` задают аргументами: это факты о
чужом проекте и чужой версии игры, и угадывать их отсюда нечем.

**Кубоиды берутся у физики.** `elements` — это `mergeVoxelBoxes`, то самое
жадное слияние, которым коллайдер разбивает модель на коробки. Слияние **точное**,
а не приближённое: множество сплошных ячеек уже есть объединение осевых кубов.
Отличается только отношение эквивалентности — физике всё равно, какого цвета
ячейка, и она сливает по «сплошной», а модели нужны коробки **одного
материала**, иначе цвет теряется на первом же слиянии. Поэтому обход один, с
параметром, а не два похожих: две реализации совпадали бы ровно до того дня,
когда перестали, и симптомом была бы коллизия, которая слегка не форма.

**Цвет живёт в текстуре.** У элемента в Minecraft своего цвета нет, поэтому
палитра запекается в картинку, а UV каждой грани указывает на её тексель.
Текстура 64×64 — сетка 16×16 из блоков 4×4, и четвёрка не украшение: одинаковые
тексели по обе стороны границы держат первые два мип-уровня чистыми, и модель с
другого конца комнаты не подмешивает соседний цвет. Ванильные UV считаются в
0..16 независимо от разрешения, так что числа в файле от этого не меняются —
запас бесплатный.

**Закопанные грани не пишутся.** Коробки — разбиение, поэтому грань закрыта
ровно тогда, когда каждая ячейка сразу за ней сплошная; проверяется весь
прямоугольник, потому что наполовину закрытую грань рисовать всё равно надо.

**Предел настоящий.** Координаты модели в Minecraft обязаны лежать в −16..32, и
сетка больше 32 отвергается, а не масштабируется молча: модель, вернувшаяся
вдвое меньше, выглядит как баг игры, а не как ошибка выгрузки.

**И честная оговорка.** У пути в C++ есть чужой декодер — MSVC. У пути в JSON
его нет: ни одна проверка здесь не может сказать, что игра файл примет. Тесты
доказывают, что текст сбалансирован, что геометрия — это геометрия модели и что
UV указывают туда, куда палитра положила цвета. Остальное — на живом
Minecraft.

## Как это проверяется

Три уровня, и каждый отвечает за своё.

| | |
|---|---|
| `scene_test_edit` | Ядро: отмена, холст, лепка, список спрайтов, три эмиттера, выгрузка в Minecraft |
| `forge selftest` | Швы самой программы: один transform, плита, наведение, обе кнопки выгрузки |
| `forge snapshot <png>` | Что окно вообще открывается и рисует |

**Про эмиттер стоит сказать отдельно.** Прогнать выгруженный исходник обратно
через `fromLayers` — это не круговой тест: `fromLayers` появилась раньше
редактора, ею пользуется рукописный код, и её собственный обход проверяет
`test_prop`. Эмиттер, перепутавший z и x, вернёт транспонированную модель, и
сверка провалится.

Чего это **не** проверяет — что текст является корректным C++. Поэтому
выгруженные файлы лежат в репозитории — `emitted_probe.hpp`, `emitted_swatch.hpp`
и `emitted_motes.hpp` в `scenes/common/` — и
включается прямо в `test_edit`: MSVC компилирует его каждой сборкой, и вот он —
чужой декодер. Побайтовая сверка с тем, что эмиттер пишет сегодня, отдельной
строкой говорит, что файл устарел; обновляется он так:

```
build\RelWithDebInfo\scenes\scene_test_edit.exe regenerate
```

`forge selftest` держит утверждение, которое ни один из двух других держать не
может: **курсор и рендерер согласны, где стоит модель.** Матрица строится один
раз и отдаётся в `PropSet::addTransformed`; наведение обращает её же. Проверка
требует, чтобы `flats()[0].toLocal` совпал с `inverseAffine` от той самой
матрицы, и чтобы луч через центр экрана попал в столбик, который там стоит. Это
тот же довод, по которому `test_rig` требует точного равенства матрицы сустава.

## Штамп модели

Вьюпорт кэшировал меш пропа по указателю и не пересобирал его никогда — до
редактора это было верно, потому что модель после размещения никто не менял.
Теперь `VoxelModel::stamp()` двигается на любое изменение, а кэш помнит, при
каком штампе собран, и пересобирает при расхождении.

Это ровно то же устройство, что у `World::chunkStamp` и `ChunkCache`, включая
причину, по которой счётчик глобальный, а не свой у каждой модели: кэши
адресуются указателем, и освобождённая модель со своей заменой по тому же
адресу сошлись бы на штампе, которого никогда не делили.

Свойство под проверкой в `test_prop`: штамп двигается на **любое** изменение
картинки и стоит, когда ничего не изменилось.

## Чего нет

- Возврата исходника обратно в редактор: `.hpp` выгружается, но не читается.
  Читается лист слоёв — это и есть его работа.
- Чтения чужого JSON: выгрузка в Minecraft идёт только наружу.
- Текстур у спрайтов во вьюпорте: квад рисуется заливкой тинта. В трассировке
  текстура работает как работала — не хватает именно предпросмотра.
- Перемещения уже поставленного спрайта: ставят и убирают, двигать нечем.
- Анимированных текстур (`.mcmeta` с `animation`) в выгрузке.
- Предпросмотра текстуры на блоке: холст выгружается в PNG, а посмотреть, как
  он ляжет на грань, пока негде.
- Своих цветов: палитра — шестнадцать фиксированных образцов. Пипетки и
  выбора цвета нет.
- Выделения, копирования и поворота области.
- Симметрии по Y и Z: зеркало только по X.
- Слоёв на холсте — см. выше, это решение, а не пропуск.
- Зеркала скина «правая рука → левая»: `mirrorX` отражает **лист**, а перенос
  между двумя прямоугольниками раскладки — другая операция.
- Вкладок для нескольких документов: их ровно три, и переключаются `Tab`.
